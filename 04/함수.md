## 1. Trino DDL — 카탈로그/스키마/테이블 등록

| 문법 | 설명 | 비고 |
|---|---|---|
| 🔵 `CREATE SCHEMA [IF NOT EXISTS] catalog.schema WITH (location = 's3a://...')` | Hive Metastore에 스키마(=데이터베이스) 등록, 이 스키마 안 테이블들의 기본 저장 위치를 지정 | `location`을 안 주면 커넥터의 기본 warehouse 경로를 씀(우리처럼 이미 존재하는 Gold 폴더를 가리키려면 명시 필수) |
| 🔵 `CREATE TABLE [IF NOT EXISTS] catalog.schema.table (col type, ...) WITH (external_location = 's3a://...', format = 'PARQUET')` | 이미 S3에 있는 parquet 폴더를 SQL 테이블로 등록(외부 테이블) | 컬럼 타입을 **직접 명시**해야 함 — DuckDB의 `read_parquet()`처럼 자동으로 스키마를 추론해주지 않음. Spark가 쓴 parquet 컬럼명/순서와 정확히 맞춰야 함 |
| ⚪ `CREATE TABLE catalog.schema.table (...)` (external_location 없이) | **관리형(managed) 테이블** 생성 — Trino가 스키마의 기본 위치 밑에 자기 소유 폴더를 새로 만들어서 관리 | 우리는 이미 Spark가 만들어둔 데이터를 "가리키기만" 하는 용도라 전부 external. 관리형은 `DROP TABLE` 시 데이터까지 같이 지워짐(외부 테이블은 메타데이터만 지워지고 실제 S3 파일은 안 지워짐) |
| ⚪ `DROP TABLE catalog.schema.table` | 테이블(메타데이터) 삭제 | 외부 테이블이면 S3 데이터는 그대로 남음 — 스키마가 바뀌어서 재등록할 때 이걸로 지우고 `CREATE TABLE`을 다시 하면 됨 |

## 2. Trino DQL — 조회

| 문법 | 설명 | 비고 |
|---|---|---|
| 🔵 `SHOW SCHEMAS IN catalog` | 카탈로그 안 스키마(데이터베이스) 목록 | Hive Metastore가 실제로 응답하는지 확인하는 가장 기본적인 헬스체크 |
| 🔵 `SHOW TABLES IN catalog.schema` | 스키마 안 테이블 목록 | |
| 🔵 `SELECT * FROM catalog.schema.table` | 일반 SQL 조회 | 표준 ANSI SQL이라 PostgreSQL/MySQL 문법과 거의 동일 |
| ⚪ `SELECT * FROM catalog.information_schema.columns WHERE table_schema = '...'` | 테이블들의 컬럼 스키마를 메타데이터로 조회 | `CREATE TABLE`에서 컬럼 타입을 잘못 넣었는지 확인할 때 유용 |
| ⚪ `EXPLAIN SELECT ...` | 실행 계획 확인 | Spark의 `.explain()`과 동일한 개념 — Trino가 S3에서 어떤 파일을 스캔할지, 어디서 필터를 미리 적용(predicate pushdown)할지 확인 가능 |

## 3. Trino CLI 실행 방식

| 명령 | 설명 | 비고 |
|---|---|---|
| 🔵 `trino --execute "SQL문"` | 단일 SQL 하나를 실행하고 결과를 CSV 비슷한 형태로 출력 | 컨테이너 안에 CLI가 내장되어 있어 `docker exec trino trino --execute "..."`로 바로 실행 가능 |
| 🔵 `trino -f 파일.sql` | 여러 SQL 문(세미콜론으로 구분)을 파일에서 읽어 순서대로 실행 | `register_gold_tables.sql`처럼 여러 `CREATE TABLE`을 한 번에 돌릴 때 사용 |
| 🔵 `trino --debug --execute "..."` | 실패 시 전체 스택트레이스까지 출력 | 기본 모드는 에러 메시지 한 줄만 나와서, 원인 파악하려면 이 옵션이 필수였음(`04/시행착오.md` 참고) |

## 4. Superset REST API — 데이터베이스 연결을 코드로 등록

| API | 설명 | 비고 |
|---|---|---|
| 🔵 `POST /api/v1/security/login` `{"username","password","provider":"db","refresh":true}` | 로그인해서 access_token 발급 | 이후 모든 API 호출에 `Authorization: Bearer <token>` 헤더 필요 |
| 🔵 `GET /api/v1/security/csrf_token/` | CSRF 토큰 발급 | 조회(GET) 아닌 쓰기 요청(POST/PUT/DELETE)엔 `X-CSRFToken` 헤더 + 같은 세션의 쿠키가 같이 필요 |
| 🔵 `POST /api/v1/database/` `{"database_name","sqlalchemy_uri","expose_in_sqllab"}` | 새 데이터베이스 연결을 등록 | 웹 UI의 "+ Database" 버튼과 동일한 동작. `sqlalchemy_uri`가 핵심 — `trino://user@host:port/catalog/schema` 형식 |
| 🔵 `GET /api/v1/database/{id}/schemas/` | 등록된 연결이 실제로 스키마 목록을 가져올 수 있는지 확인 | 연결 테스트 용도로 사용(정상이면 Trino가 보는 스키마 그대로 반환) |
| ⚪ `GET /api/v1/dashboard/` / `GET /api/v1/chart/` | 만들어진 대시보드/차트 목록 조회 | 코드로 뭐가 만들어져 있는지 확인할 때(웹 UI 안 열어봐도 됨) |
| ⚪ `POST /api/v1/dataset/` | 데이터셋(테이블을 Superset이 인식하는 단위로 등록)을 API로 생성 | 우리는 SQL Lab에서 "Save as Dataset"으로 UI로 만들었음 — API로도 가능(자동화하려면 이쪽) |

## 5. SQLAlchemy 연결 문자열(URI) 형식

| 형식 | 설명 | 비고 |
|---|---|---|
| 🔵 `trino://user@host:port/catalog/schema` | Trino용 SQLAlchemy URI | `catalog`/`schema`는 선택(생략하면 쿼리에서 매번 `catalog.schema.table`로 풀네임 지정 필요). 인증 없는 로컬 환경이라 비밀번호 없이 `user@`만 씀 |
| ⚪ `trino://user:password@host:port/catalog` | 인증이 필요한 Trino(LDAP/Kerberos 등)에 접속할 때 | 우리 환경(`hive.security=ALLOW_ALL`)은 인증 자체가 없어서 불필요 |
