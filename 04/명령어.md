# 04 명령어 정리

`02/명령어.md`(docker/kubectl), `03/명령어.md`(Airflow)에 이어서, **Trino/Hive Metastore/Superset 스택 특유의 명령어**만 정리.

- 🔵 = 이 저장소 작업 중 실제로 사용함
- ⚪ = 아직 안 썼지만 알아두면 좋음

---

## 1. Docker Compose (04 전용)

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `cd 04 && docker compose up -d` | Hive Metastore + Trino + Superset 기동 | 02(k3s+MinIO)가 먼저 떠 있어야 함(네트워크를 `external: true`로 참조) |
| 🔵 `docker compose up -d --force-recreate <서비스명>` | 설정 파일(catalog properties, bootstrap 스크립트 등)을 고친 뒤 해당 컨테이너만 완전히 재생성 | 단순 `restart`로는 이미지 재빌드/entrypoint 재실행이 안 되는 경우가 있어서, 설정 변경 후엔 이 방식이 확실함 |
| 🔵 `docker compose restart trino` | 볼륨 마운트된 설정 파일(`etc/`)만 바꿨을 때 | 바인드 마운트라 컨테이너 재생성 없이 재시작만 해도 새 파일 내용을 바로 읽음 |

## 2. Trino — 컨테이너 안에서 SQL 실행

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `docker exec trino trino --execute "SQL문"` | 단발성 쿼리 실행 | 결과가 커서 확인하기 어려우면 `LIMIT` 붙이기 |
| 🔵 `docker exec trino trino --debug --execute "SQL문"` | 실패 시 전체 스택트레이스 확인 | 원인 불명 에러는 항상 이걸로 먼저 재현 |
| 🔵 `docker cp 파일.sql trino:/tmp/파일.sql` 후 `docker exec trino trino -f /tmp/파일.sql` | 여러 SQL문을 한 번에 실행 | `register_gold_tables.sql` 같은 여러 `CREATE TABLE`을 순서대로 돌릴 때 |
| 🔵 `docker inspect trino --format '{{.RestartCount}}'` | 컨테이너가 재시작 루프에 빠졌는지 확인 | `docker ps`의 `Up 몇 초`가 계속 반복되면 이걸로 확정 진단 |

## 3. Hive Metastore — 내부 상태/로그 확인

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `docker exec hive-metastore sh -c "cat /opt/hive/conf/core-site.xml"` | 실제로 적용된 설정 파일 확인 | 마운트/커스텀 conf 메커니즘이 제대로 작동했는지는 반드시 컨테이너 안에 직접 들어가서 확인해야 함(겉으로는 정상 기동한 것처럼 보여도 설정이 안 먹었을 수 있음) |
| 🔵 `docker exec hive-metastore sh -c "tail -c 8000 /tmp/hive/*.log"` | Hive Metastore의 실제 서버 로그(`hive.log`) | `docker logs`에는 시작 시점 로그만 나오고, 쿼리 처리 중 에러는 컨테이너 내부의 이 파일에 별도로 쌓임 |
| 🔵 `docker exec hive-metastore sh -c "export HADOOP_CLASSPATH=/opt/hive/auxlib/*; hadoop --config /hive_custom_conf fs -ls s3a://버킷/"` | Hive/Trino를 거치지 않고 Hadoop S3A 연결 자체를 직접 테스트 | 문제가 "S3A 설정 자체"인지 "Hive Metastore 코드"인지 구분할 때 결정적이었음(`04/시행착오.md` 3번) |

## 4. Superset — 컨테이너 안에서 디버깅

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `docker exec superset python -c "import sys; [print(p) for p in sys.path]"` | 실제 모듈 탐색 경로 확인 | `pip install`이 성공해도 엉뚱한 위치(venv 아닌 user-site)에 깔리는 경우가 있어서, "설치됨"과 "import 가능함"을 분리해서 확인해야 함 |
| 🔵 `docker exec superset pip show 패키지명` | 설치된 패키지의 메타데이터(버전, 설치 위치, 의존성) 확인 | `Location` 필드로 venv/user-site 여부 판단 |
| 🔵 `docker exec superset python -c "from sqlalchemy import create_engine; e=create_engine('trino://...'); ..."` | Superset UI를 거치지 않고 SQLAlchemy 연결 자체를 코드로 테스트 | UI 로그인 없이도 연결 문제인지 UI 문제인지 좁힐 수 있음 |
| ⚪ `docker exec superset superset shell` | Superset의 Python/Flask 셸 진입 | ORM 모델을 직접 다루며 디버깅할 때(우리는 REST API로 충분해서 안 씀) |

## 5. curl로 헬스체크/API 직접 호출

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `curl -s -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8889/health` | Superset이 응답하는지 HTTP 상태 코드만 빠르게 확인 | 컨테이너가 `Up`이어도 애플리케이션 자체는 아직 안 떴을 수 있어서(`health: starting`), 실제 응답 여부를 별도로 확인 |
| ⚪ `curl -X POST http://localhost:8889/api/v1/security/login -H "Content-Type: application/json" -d '{...}'` | 터미널에서 직접 REST API 호출(파이썬 없이) | 컨테이너 안이 아니라 호스트에서 바로 API를 두드리고 싶을 때 |

## 6. Windows(Git Bash) 특유의 주의사항

| 상황 | 조치 | 비고 |
|---|---|---|
| 🔵 `docker exec <컨테이너> ls /opt/...` 같은 명령이 `C:/Program Files/Git/opt/...`로 잘못 해석됨 | `export MSYS_NO_PATHCONV=1` 먼저 실행 | Git Bash(MSYS)가 `/`로 시작하는 인자를 Windows 경로로 자동 변환하는 게 원인. 컨테이너 **내부** 경로를 다룰 땐 이 변환을 꺼야 함 |
| 🔵 `docker cp 호스트경로 컨테이너:경로`처럼 호스트/컨테이너 경로가 같이 들어가는 명령 | `MSYS_NO_PATHCONV`를 다시 `unset` | 이 경우엔 호스트 경로 쪽은 변환이 **필요**해서 켜져 있으면 오히려 실패함(`GetFileAttributesEx` 에러) — 상황별로 켜고 꺼야 함 |
