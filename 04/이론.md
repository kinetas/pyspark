# 쿼리 엔진 & 데이터 시각화 이론 정리

`02`(Spark 이론), `03`(오케스트레이션 이론)에 이어, **"저장된 데이터를 SQL로 조회하고 차트로 보여주는" 단계**의 이론. 크게 두 부분 — (1) Trino/Hive Metastore 같은 쿼리 엔진이 왜 필요하고 어떻게 동작하는지, (2) 데이터 성격에 따라 어떤 차트를 골라야 하는지.

**중요도 기준**
- ★★★ = 실무/면접에서 계속 나오는 핵심 개념
- ★★ = 알아두면 설계/트러블슈팅에 바로 도움 되는 것
- ★ = 심화/참고

---

# Part 1. 쿼리 엔진 이론

## 1장. Data Lake는 그 자체로 SQL 조회가 안 된다 ★★★

`02/아키텍처.md`에서 정리한 대로 MinIO(Data Lake)는 파일을 그대로 저장할 뿐, "테이블"이라는 개념이 없음. `spark.read.parquet(path)`처럼 **어떤 프로그램이 명시적으로 그 경로를 읽어야만** 데이터에 접근 가능. 반면 우리가 익숙한 "SQL로 `SELECT * FROM 테이블`" 같은 조회는 그 앞에 항상 **"이 이름의 테이블은 이 경로에, 이런 스키마로 있다"는 걸 아는 무언가**가 있어야 함 — 그게 이번 장의 주제.

## 2장. Schema-on-Read와 외부 테이블(External Table) ★★★

- **Schema-on-Write**(전통적 RDB): 데이터를 쓰는 시점에 스키마를 강제. 테이블을 먼저 만들고 그 구조에 맞는 데이터만 넣을 수 있음.
- **Schema-on-Read**(Data Lake/Lakehouse): 데이터는 그냥 파일로 저장해두고, **읽는 시점에** "이걸 이런 스키마로 해석하겠다"고 선언. 우리가 `CREATE TABLE ... WITH (external_location = 's3a://...')`로 한 게 바로 이것 — 이미 존재하는 parquet 파일 더미에 사후적으로 스키마를 씌운 것.
- **외부 테이블(External Table)**: 메타스토어는 "위치 + 스키마" 정보만 갖고, 실제 데이터 파일의 생명주기(생성/삭제)는 책임지지 않음. `DROP TABLE`을 해도 S3의 실제 파일은 안 지워짐 — 메타데이터만 지워짐. 반대 개념인 **관리형(Managed) 테이블**은 테이블 자체가 데이터의 소유자라 `DROP TABLE`하면 데이터도 같이 삭제됨.
- 우리 구조에서 데이터의 진짜 주인은 **Spark 파이프라인**(파일을 실제로 쓰는 주체)이고, Hive Metastore/Trino는 그 위에 "조회용 스키마"만 얹은 것 — 그래서 전부 external table로 등록함.

## 3장. Hive Metastore: 여러 엔진이 공유하는 카탈로그 ★★★

- Hive Metastore는 원래 이름 그대로 Apache Hive를 위해 만들어졌지만, 지금은 **사실상 업계 표준 메타데이터 저장소**로 굳어져서 Hive뿐 아니라 Spark, Trino, Presto 등 서로 다른 엔진이 **같은 메타스토어를 공유**해서 쓸 수 있음.
- 이게 왜 중요한가: 한 번 `CREATE TABLE`로 등록해두면, Spark로 써도 Trino로 읽어도 같은 테이블 정의를 씀 — "테이블이 뭔지"에 대한 합의가 여러 도구 사이에 깨지지 않음. AWS Glue Data Catalog(관리형), Trino/Presto 자체 REST 카탈로그, Unity Catalog(Databricks) 등도 전부 이 "공유 카탈로그" 역할을 하는 서로 다른 구현체들.
- 우리는 실습 규모라 Hive Metastore 하나만 두고 Trino에서만 읽지만, 원한다면 같은 메타스토어를 Spark 쪽(`03`의 `02.py`/`03.py`)에서도 붙여서 "Spark가 쓴 테이블을 Trino가 그대로 인식"하게 만들 수도 있음(지금은 안 함 — Spark는 경로를 직접 알고 쓰기 때문에 메타스토어가 없어도 동작).

## 4장. MPP 쿼리 엔진 ★★

- **MPP(Massively Parallel Processing)**: 하나의 쿼리를 여러 노드에 나눠서 병렬로 처리하는 방식. Trino/Presto가 여기 속함 — 개념적으로 Spark의 Driver/Executor 구조(`02/이론.md` 2장)와 매우 비슷함(Trino의 Coordinator ≈ Spark Driver, Trino의 Worker ≈ Spark Executor).
- 우리 구성은 `node-scheduler.include-coordinator=true`로 **coordinator 혼자 worker 역할까지 겸함**(별도 worker 컨테이너 없음) — 학습 규모라 단일 노드로 충분하지만, 실무에서는 coordinator 1대 + worker 여러 대로 수평 확장.
- **Trino vs Spark, 언제 뭘 쓰나 ★★**: 겹치는 영역도 있지만 대체로 이렇게 나뉨 — Trino는 "이미 정제된 데이터를 빠르게 SQL로 조회/집계"(대화형 쿼리, BI 백엔드)에 강하고, Spark는 "무거운 배치 변환/ML/복잡한 파이프라인 로직"(우리 Bronze→Silver→Gold)에 강함. 그래서 지금 구조가 "Spark로 변환 → Trino로 서빙"인 것.

## 5장. Predicate/Projection Pushdown ★

- **Predicate Pushdown**: `WHERE` 조건을 파일을 다 읽고 나서 거르는 게 아니라, 애초에 필요한 파일/row group만 골라서 읽는 최적화. Parquet은 파일 안에 컬럼별 min/max 통계를 갖고 있어서, 이 정보만 보고 "이 파일엔 조건에 맞는 값이 없다"를 미리 판단해 통째로 건너뛸 수 있음.
- **Projection Pushdown**: `SELECT col1, col2`처럼 일부 컬럼만 요청하면, Parquet의 컬럼형 저장 구조 덕분에 나머지 컬럼은 아예 안 읽음(`02/이론.md`의 Parquet 관련 설명과 연결).
- `EXPLAIN SELECT ...`로 실제로 이런 최적화가 적용되는지 확인 가능(`04/함수.md` 참고).

# Part 2. 데이터 시각화 이론

## 6장. 차트를 고르기 전에: 데이터가 어떤 "관계"를 표현하는가 ★★★

차트 선택의 출발점은 "이 데이터로 어떤 종류의 관계/질문에 답하려는가"임. 크게 5가지로 나뉨:

| 관계 유형 | 질문의 형태 | 대표 차트 |
|---|---|---|
| **비교(Comparison)** | 항목 간 크기를 비교 | Bar Chart |
| **추세(Trend)** | 시간에 따라 어떻게 변했나 | Line Chart, Area Chart |
| **구성(Composition)** | 전체 중 각 부분의 비중 | Stacked Bar, (제한적으로) Pie |
| **분포(Distribution)** | 값들이 어떻게 퍼져있나 | Histogram, Box Plot |
| **관계(Relationship)** | 두 변수가 서로 연관 있나 | Scatter Plot |

## 7장. 비교(Comparison) — Bar Chart ★★★

- 범주형 축(카테고리, 브랜드 등) + 숫자 지표(매출, 개수 등) 조합엔 Bar Chart가 기본값.
- **정렬이 핵심**: 값 기준으로 내림차순 정렬 안 하면 눈으로 비교하기 어려움 — 우리가 만든 `brand_revenue` 차트도 매출 합계 기준 정렬이 되어야 "가장 잘 팔리는 브랜드"가 한눈에 보임.
- **Top N 처리**: `category_code`처럼 카테고리 종류가 많으면 전부 다 보여주지 말고 상위 N개(보통 10~20개)만 + "기타"로 묶는 게 가독성이 좋음. Superset 차트 설정의 `Row Limit`이 이 역할.
- 가로 막대(Horizontal Bar) vs 세로 막대(Vertical Bar): 카테고리 이름이 길면 가로형이 라벨 겹침을 피하기 좋음.

## 8장. 추세(Trend) — Line/Area Chart ★★★

- 시간(날짜/시각) 축이 있는 데이터는 거의 항상 Line Chart. 우리 `daily_events`/`daily_purchase`가 정확히 이 케이스(`event_date` 컬럼).
- Line vs Area: 값 자체의 변화 패턴이 궁금하면 Line, "크기감"(누적된 양의 느낌)까지 보여주고 싶으면 Area — 단 여러 계열을 Area로 겹치면 오히려 안 보일 수 있어서 계열이 2~3개 이하일 때 추천.
- **X축은 반드시 시간순 정렬**, 그리고 시간 간격이 균일한지 확인(하루 빠진 날짜가 있으면 선이 왜곡되어 보일 수 있음).

## 9장. 구성(Composition) — Pie/Donut의 함정 ★★★

- Pie/Donut 차트는 "전체 대비 비중"을 보여주는 데 쓰이지만, **실무에서는 의외로 지양되는 경우가 많음**: 사람 눈은 각도/면적보다 길이(막대)를 비교하는 데 훨씬 정확함. 조각이 3~4개를 넘어가면 크기 차이를 거의 구분 못 함.
- **대안**: 비중 비교가 목적이면 정렬된 Bar Chart(또는 100% Stacked Bar)가 대부분 더 명확함. Pie는 "정확히 2~3개 항목의, 차이가 뚜렷한 비중"을 보여줄 때만 제한적으로 유효.
- `event_funnel`처럼 "단계별로 줄어드는" 데이터는 Pie가 아니라 **Funnel Chart**(퍼널 전용 차트, view→cart→purchase 같은 이탈률 시각화에 특화)가 정확히 맞는 형태.

## 10장. 분포(Distribution) — Histogram/Box Plot/Table ★★

- 값들이 어떻게 퍼져 있는지(평균, 중앙값, 이상치 등)가 궁금하면 Bar/Line이 아니라 분포 전용 차트가 필요.
- 우리 `price_stats`/`purchase_price_stats`는 Spark `.describe()`가 이미 count/mean/stddev/min/max로 **요약을 다 해놓은 상태**라, 이걸 또 차트로 그리기보다는 **Table**로 그대로 보여주는 게 오히려 명확함(이미 숫자 몇 개뿐이라 시각화의 이점이 적음).
- `price_percentiles`(p25/median/p75/p95)는 항목이 4개뿐이라 Bar Chart로 구간별 값을 비교하기 좋음. 원본 raw 데이터(개별 row의 price 분포 전체)가 있었다면 Histogram이나 Box Plot이 더 적합했겠지만, 우리는 이미 percentile로 집계된 결과만 갖고 있어서 Bar로 충분.

## 11장. 관계(Relationship) — Scatter Plot ★

- 두 숫자 변수 사이에 상관관계가 있는지 보고 싶을 때(예: "가격이 높을수록 구매전환율이 낮은가"). 우리 Gold 테이블 중에는 이 관계를 직접 보여주는 게 없지만, 예를 들어 `category_revenue`의 `revenue`와 `purchase_count`를 x/y로 놓으면 "매출은 높은데 구매건수는 적은(=객단가가 높은) 카테고리"를 찾는 식으로 활용 가능.

## 12장. 흔한 실수 — 오해를 부르는 시각화 ★★★

- **Y축을 0부터 시작하지 않는 Bar Chart**: 막대 높이 차이가 실제 값 차이보다 과장되어 보임 — Bar Chart는 반드시 0부터 시작해야 함(Line Chart는 추세만 보여주는 목적이면 예외적으로 허용되기도 함).
- **범례가 너무 많은 색상 구분**: 계열이 7~8개를 넘어가면 색으로 구분이 사실상 불가능 — Top N + 기타로 줄이거나 여러 개의 작은 차트(Small Multiples)로 나누는 게 나음.
- **Big Number(단일 숫자) 카드 남용**: KPI 하나(총 매출, 총 이벤트 수 등)를 강조할 땐 좋지만, 맥락(전 기간 대비 증감 등) 없이 숫자만 던지면 "그래서 좋은 건지 나쁜 건지" 판단이 안 됨 — 가능하면 전기 대비 증감률과 함께 배치.
- **차트 종류보다 먼저 확인할 것**: "이 숫자가 합계(SUM)인지 평균(AVG)인지 개수(COUNT)인지"부터 명확히 하기 — Superset의 Metric 설정에서 집계 함수를 잘못 고르면 차트 모양이 멀쩡해도 숫자 자체가 틀림.
