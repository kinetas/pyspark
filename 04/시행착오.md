# 2026-08-04 시행착오 정리 (Trino + Hive Metastore + Superset)

Gold 레이어를 실무형 쿼리 엔진(Trino)+BI 도구(Superset)로 조회하는 스택을 처음부터 구축하며 겪은 문제들. 하나같이 "설정 하나만 틀려도 조용히/이상하게 실패하는" 종류라, 각 원인을 어떻게 좁혀갔는지까지 기록한다.

---

## 1. Trino 카탈로그가 재시작 루프에 빠짐 — 리전(region) 누락

**증상**: `docker ps`에서 `trino`만 계속 "Up 몇 초"로 나옴(다른 컨테이너는 몇 분/시간 단위인데). `docker inspect trino --format '{{.RestartCount}}'`로 확인하니 21번 재시작됨.

**원인 파악**: 재시작 루프는 컨테이너가 뜨자마자 죽는다는 뜻이라 로그부터 확인. `SdkClientException: Unable to load region from any of the providers in the chain` — AWS SDK가 리전을 못 찾아서 카탈로그 로딩 자체가 실패하고 있었음. MinIO는 AWS가 아니라서 리전을 자동으로 알 수 없는데, Trino의 S3 커넥터가 그래도 리전 값을 요구함.

**해결**: 카탈로그 프로퍼티(`04/trino/etc/catalog/minio_lake.properties`)에 `s3.region=us-east-1`(아무 값이나 무방, MinIO는 실제로 리전을 안 씀) 추가.

## 2. Hive Metastore의 S3 접속 — AWS SDK v1 vs v2 버전 불일치

**증상**: `CREATE SCHEMA ... WITH (location = 's3a://...')` 실행 시 `NumberFormatException: For input string: "60s"` 발생 (`HIVE_METASTORE_ERROR`).

**원인 파악**: 에러 자체는 뜬금없어 보였지만, 이미지에 내장된 Hadoop 버전(`docker exec hive-metastore sh -c "ls /opt/hadoop/share/hadoop/common/*.jar"`)이 **3.4.1**인데, hadoop-aws jar를 3.3.6으로 잘못 넣어놨던 게 원인. Hadoop 3.4.x부터 S3A가 AWS SDK v1(`aws-java-sdk-bundle`) 대신 **AWS SDK v2**(`software.amazon.awssdk:bundle`)를 쓰도록 바뀌어서, 구버전 SDK가 클래스패스에 섞여 들어가며 설정값 파싱 방식이 꼬였음.

**해결**: Maven Central의 `hadoop-aws:3.4.1` pom(`hadoop-project:3.4.1`의 `aws-java-sdk-v2.version` 프로퍼티)에서 정확한 짝을 확인 → `hadoop-aws-3.4.1.jar` + `bundle-2.24.6.jar`(AWS SDK v2)로 교체.

```bash
curl -sL -o hadoop-aws-3.4.1.jar https://repo1.maven.org/maven2/org/apache/hadoop/hadoop-aws/3.4.1/hadoop-aws-3.4.1.jar
curl -sL -o bundle-2.24.6.jar https://repo1.maven.org/maven2/software/amazon/awssdk/bundle/2.24.6/bundle-2.24.6.jar
```

**교훈**: hadoop-aws는 반드시 이미지에 내장된 hadoop-common과 **정확히 같은 버전**을 써야 함. 다른 곳(02/03)에서 검증됐던 `3.3.4` 조합을 그대로 재사용하면 안 되는 이유가 여기 있음 — 이미지마다 내장 Hadoop 버전이 다르면 짝도 다시 맞춰야 함.

## 3. `HIVE_CUSTOM_CONF_DIR`가 조용히 무시됨 — 이미지에 `find` 없음

**증상**: jar 버전을 고친 뒤에도 `CREATE SCHEMA`가 여전히 실패(`Failed to create external path ... null`). 메시지가 "null"이라 단서가 없었음.

**원인 파악**:
1. `docker exec hive-metastore ... hadoop fs -mkdir s3a://test-bucket/...`로 **같은 설정을 CLI에서 직접 주니 성공** — 이게 Hadoop/S3A 자체 문제가 아니라 **메타스토어 서버 프로세스에 설정이 안 들어가고 있다**는 뜻으로 좁혀짐.
2. `docker exec hive-metastore cat /opt/hive/conf/core-site.xml` → 파일이 아예 없음. `HIVE_CUSTOM_CONF_DIR=/hive_custom_conf`로 마운트해뒀는데 실제 conf 디렉토리에 반영이 안 됨.
3. 컨테이너의 시작 로그(`docker logs hive-metastore`, entrypoint가 `set -x`로 모든 명령을 그대로 찍어줌)를 처음부터 다시 봄 → `find: command not found`. 커스텀 conf를 심볼릭 링크로 복사하는 로직(`find "$HIVE_CUSTOM_CONF_DIR" -type f -exec ln -sfn {} "$HIVE_CONF_DIR"/ \;`)이 이 이미지(RHEL UBI 기반, `find` 미포함)에서 조용히 실패하고 있었음. `set -e`가 아니라서 에러가 나도 스크립트가 안 멈추고 계속 진행됨.

**해결**: `HIVE_CUSTOM_CONF_DIR` 메커니즘을 아예 안 쓰고, `core-site.xml`을 `/opt/hive/conf/core-site.xml`에 **직접 바인드 마운트**.

**교훈**: 컨테이너가 "정상적으로 뜬 것처럼" 보여도(재시작 루프 없이 계속 Up 상태) 내부 설정이 실제로 반영 안 됐을 수 있음 — `docker exec`로 설정 파일이 진짜 그 자리에 있는지 직접 들어가서 확인하는 습관이 필요함. 특히 `set -x`로 모든 실행 명령을 로그에 남기는 entrypoint는 이런 조용한 실패를 잡는 데 결정적이었음.

## 4. Windows Git Bash + `docker exec`의 경로 자동 변환

**증상**: `docker exec hive-metastore ls -la /opt/hive/` 같은 명령이 `ls: cannot access 'C:/Program Files/Git/opt/hive/'` 같은 엉뚱한 에러를 냄.

**원인**: Git Bash(MSYS)가 `/`로 시작하는 인자를 자동으로 Windows 경로로 변환해버림 — 컨테이너 **내부** 경로(`/opt/hive/`)인데 호스트 경로로 오해하고 변환한 것.

**해결**: `export MSYS_NO_PATHCONV=1` 후 `docker exec` 실행. 단, `docker cp <호스트경로> container:<컨테이너경로>`처럼 호스트 경로와 컨테이너 경로가 **한 명령에 같이 들어가는 경우**는 반대로 이 변환이 필요해서, 그럴 땐 `MSYS_NO_PATHCONV`를 다시 꺼야 함(`unset`) — 상황마다 켜고 꺼야 하는 게 번거로움.

## 5. Superset — pip install이 venv를 못 찾고 엉뚱한 곳에 깔림

**증상**: Superset 부트스트랩 스크립트에서 `pip install trino sqlalchemy-trino` 실행은 성공했는데, 정작 `python -c "import sqlalchemy_trino"`는 `ModuleNotFoundError`.

**원인 파악**: `docker exec superset python -c "import sys; print(sys.path)"`로 실제 모듈 탐색 경로를 확인 → `/app/.venv/lib/python3.10/site-packages`(Superset가 쓰는 venv)는 있는데, pip이 설치한 위치인 `/app/superset_home/.local/lib/...`(user-site)는 빠져있었음. Superset 컨테이너가 venv에 쓰기 권한이 없는 유저로 도는 바람에 `pip install`이 조용히 `--user` 설치로 폴백된 것.

**1차 해결(그리고 새로 발생한 문제)**: `PYTHONPATH`에 user-site 경로를 명시적으로 추가했더니 이번엔 Superset 자체가 기동 실패(`ImportError: cannot import name 'eagerload' from 'sqlalchemy.orm'`). 확인해보니 `pip install sqlalchemy-trino`가 의존성으로 **SQLAlchemy 2.0.51**을 딸려 설치했는데, 이게 PYTHONPATH 우선순위 때문에 Superset 코어가 원래 쓰던(venv에 고정된) **SQLAlchemy 1.4.54**를 가려버림 — `eagerload`는 SQLAlchemy 2.0에서 제거된 구버전 API라 Superset이 아예 못 뜸.

**최종 해결**: 애초에 `sqlalchemy-trino`라는 별도 패키지가 필요 없었음 — 최신 `trino` 파이썬 클라이언트(0.338.0)가 `trino.sqlalchemy`로 SQLAlchemy 다이얼렉트를 **자체 내장**하고 있음(PyPI의 `sqlalchemy-trino`는 사실상 빈 메타데이터만 있는 사장된 패키지였음, 설치해보니 `.dist-info`만 있고 실제 모듈 파일이 없었음). `pip install trino`만 하고, `PYTHONPATH`에 user-site 경로만 추가하는 것으로 정리.

**교훈**: 의존성 있는 패키지를 설치할 때 "왜 이 패키지가 필요하다고 생각했는지"부터 재확인할 가치가 있음 — 상위 라이브러리(`trino`)가 이미 필요한 기능을 내장하고 있는 경우가 생각보다 흔함.

## 6. 전체 검증 순서 (문제 없이 통과한 부분)

문제들을 다 고친 뒤 실제로 끝까지 확인한 절차:

1. `docker exec trino trino --execute "SHOW SCHEMAS IN minio_lake"` → Hive Metastore 연결 확인
2. `CREATE SCHEMA ... WITH (location = 's3a://test-bucket/gold/')` → 메타스토어의 S3 쓰기 권한 확인
3. `CREATE TABLE ... WITH (external_location = ..., format = 'PARQUET')` 8개 (`04/register_gold_tables.sql`) → 실제 Gold parquet 스키마 등록
4. `SELECT * FROM minio_lake.gold.event_funnel` 등으로 진짜 데이터 조회 확인 (Spark가 만든 집계 결과와 일치)
5. Superset REST API(`/api/v1/security/login` → `/api/v1/database/`)로 Trino 연결을 미리 등록 → 로그인만 하면 바로 SQL Lab에서 조회 가능한 상태로 완성
