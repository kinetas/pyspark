## 1. DAG 정의

| API | 설명 | 비고 |
|---|---|---|
| 🔵 `with DAG(dag_id=..., ...) as dag:` | DAG(파이프라인) 객체를 컨텍스트 매니저로 생성. 이 블록 안에서 만든 Operator들이 자동으로 이 DAG에 소속됨 | `dag_id`는 Airflow 전체에서 유일해야 함(웹 UI 목록/URL에 그대로 노출) |
| 🔵 `description="..."` | 웹 UI DAG 목록에 표시되는 한 줄 설명 | 기능에 영향 없음, 사람이 보는 용도 |
| 🔵 `start_date=datetime(2026, 8, 1)` | 이 DAG가 "스케줄상 유효해지는" 기준 시점 | **흔한 오해**: "이 날짜에 자동 실행된다"가 아니라 "이 날짜 이전 구간은 스케줄 대상이 아니다"라는 하한선. 실제 실행 여부는 `schedule` + `catchup`이 결정 |
| 🔵 `schedule=None` | 자동 스케줄 안 함 — 수동 트리거(웹 UI ▶ 버튼, `airflow dags trigger`)로만 실행 | `"@daily"`, `"0 9 * * *"`(cron 표현식) 등을 넣으면 자동 반복 실행으로 바뀜 |
| 🔵 `catchup=False` | `start_date`부터 지금까지 스케줄이 밀린 구간을 한꺼번에 백필(backfill)하지 않음 | `schedule=None`이면 사실상 의미 없지만, 나중에 `"@daily"`로 바꿀 때 `True`(기본값)로 두면 과거 구간이 전부 몰아서 실행되는 사고가 날 수 있어 미리 명시해둠 |
| 🔵 `tags=["spark", "k8s", "medallion"]` | 웹 UI DAG 목록 필터링용 라벨 | 순수 UI 편의 기능, 실행에 영향 없음 |
| 🔵 `params={"kaggle_file": "2019-Oct.csv"}` | Trigger DAG 시 오버라이드 가능한 기본 파라미터 | 태스크 안에서 `{{ params.kaggle_file }}` 형태(Jinja 템플릿)로 참조. 트리거할 때 config로 `{"kaggle_file": "2019-Nov.csv"}`를 주면 이 값이 덮어씀 |

## 2. Operator — 태스크의 실제 동작 정의

| API | 설명 | 비고 |
|---|---|---|
| 🔵 `KubernetesPodOperator(...)` | 태스크 하나 = K8s 팟 하나를 새로 띄워서 실행 | `airflow.providers.cncf.kubernetes.operators.pod`. 기본 이미지엔 없어서 `_PIP_ADDITIONAL_REQUIREMENTS`로 provider 별도 설치 필요(`03/시행착오_0803-0804.md` 참고) |
| 🔵 `task_id="..."` | DAG 안에서 이 태스크를 가리키는 유일 식별자 | 웹 UI Grid 뷰, 로그 URL 등에 그대로 노출 |
| 🔵 `name="..."` | 실제로 생성되는 K8s 팟 이름의 접두어 | Airflow가 실행마다 랜덤 suffix를 붙여 유일하게 만들어줌(재실행 시 이름 충돌 방지) |
| 🔵 `image="..."` | 팟이 쓸 컨테이너 이미지 | `cmds`/`arguments`가 이 이미지 안에서 실행됨 |
| 🔵 `cmds=[...]` / `arguments=[...]` | 컨테이너의 entrypoint 커맨드와 인자 | `cmds`는 실행 파일, `arguments`는 그 뒤에 붙는 인자 목록(우리는 `spark-submit`을 `cmds`로, `--master ...` 등을 `arguments`로 분리) |
| 🔵 `service_account_name="spark"` | 이 팟이 사용할 K8s ServiceAccount | Spark driver 팟이 executor 팟을 만들 권한(RBAC)이 여기서 나옴 — 없으면 `Forbidden` 에러(`02/start.md` 시도5~6 참고) |
| 🔵 `config_file=KUBE_CONFIG_PATH` | Airflow 컨테이너 안에서 어떤 kubeconfig 파일로 K8s에 접속할지 | `kubeconfig-prep` 컨테이너가 미리 만들어 둔 파일 경로. Airflow 자체가 K8s 안에서 도는 게 아니라 **밖에서 K8s API로 팟 생성을 요청**하는 구조라서 필요(`in_cluster=False`와 짝) |
| 🔵 `in_cluster=False` | Airflow가 K8s 클러스터 "내부"에서 도는 게 아니라 "외부 클라이언트"로서 접속함을 명시 | `True`면 팟 안에 자동 마운트되는 서비스어카운트 토큰을 쓰려고 시도(우리 구조와 다름) |
| 🔵 `get_logs=True` | 생성된 팟의 stdout을 Airflow 태스크 로그로 그대로 스트리밍 | 이게 없으면 매번 `kubectl logs`를 따로 쳐야 함 — 사실상 필수 옵션 |
| 🔵 `is_delete_operator_pod=True` | 태스크가 끝나면(성공/실패 무관) 팟을 자동 삭제 | 없으면 재실행마다 팟이 계속 쌓여서 `kubectl delete pod --force`를 손으로 반복해야 함(02 시절 겪던 번거로움) |
| 🔵 `startup_timeout_seconds=300` | 팟이 이 시간 안에 뜨지 않으면 태스크 실패 처리 | 이미지 pull이 느리거나 리소스가 부족해 스케줄링이 안 될 때의 안전장치 |
| 🔵 `secrets=[Secret(...), ...]` | K8s Secret의 값을 팟 환경변수로 주입 | 아래 3번 참고 |
| 🔵 `env_vars={...}` | 팟에 직접 넣을 환경변수(Secret이 아닌 값) | 문자열 값에 `{{ params.x }}` 같은 Jinja 템플릿 사용 가능(템플릿 필드로 등록되어 있는 파라미터라서) |
| 🔵 `container_resources={"requests": {...}, "limits": {...}}` | 팟의 CPU/메모리 요청량/제한량 | `ingest_task`에만 지정(가벼운 작업). Spark job은 `spark-submit --conf`로 driver/executor 메모리를 따로 제어하므로 별도 지정 안 함 |
| ⚪ `BashOperator` | 셸 명령 하나를 실행하는 가장 단순한 Operator | 우리는 안 씀(모든 실제 작업이 K8s 팟 안에서 돌아야 해서 `KubernetesPodOperator`로 통일) — 하지만 Airflow 학습 자료에서 가장 먼저 나오는 예제라 알아두면 좋음 |
| ⚪ `PythonOperator` / `@task` (TaskFlow API) | 파이썬 함수 하나를 태스크로 실행 | 이것도 Airflow 스케줄러가 도는 컨테이너 **안에서** 직접 실행되는 방식이라, 우리처럼 "무거운 연산은 별도 팟에서"라는 설계와는 안 맞음. 가벼운 분기/알림 로직에는 유용 |

## 3. Secret — K8s Secret을 팟 환경변수로 주입

| API | 설명 | 비고 |
|---|---|---|
| 🔵 `Secret("env", "KAGGLE_USERNAME", "kaggle-credentials", "username")` | K8s Secret `kaggle-credentials`의 `username` 키 값을 팟 환경변수 `KAGGLE_USERNAME`으로 주입 | `airflow.providers.cncf.kubernetes.secret.Secret`. 인자 순서: `deploy_type("env"/"volume")`, `deploy_target(환경변수명)`, `secret(K8s Secret 이름)`, `key(Secret 안 키 이름)` |
| 🔵 `KubernetesPodOperator(secrets=KAGGLE_SECRETS + MINIO_SECRETS, ...)` | 여러 `Secret` 객체를 리스트로 합쳐서 한 번에 주입 | DAG 코드 어디에도 실제 자격증명 값이 안 적힘 — 값은 K8s Secret 안에만 존재(사전에 `kubectl create secret`으로 생성, `03/실행_가이드.md` 3번 참고) |

## 4. 태스크 의존성 정의

| API | 설명 | 비고 |
|---|---|---|
| 🔵 `task_a >> task_b` | `task_a`가 끝난 뒤에 `task_b`를 실행하도록 순서 지정 | `set_downstream()`의 문법 설탕(syntactic sugar). 실제 병렬 실행 여부는 Executor 종류에 달림(6번 참고) |
| 🔵 `ingest_task >> bronze_task >> silver_task >> gold_task` | 여러 개를 체이닝해서 순차 파이프라인 구성 | 우리 DAG 전체 의존성이 이 한 줄. 기본적으로 앞 태스크가 **성공**해야 다음이 실행됨(실패 시 다음 태스크는 `upstream_failed`로 스킵) |
| ⚪ `[task_a, task_b] >> task_c` | `task_a`, `task_b`를 병렬로 실행한 뒤 둘 다 끝나면 `task_c` | 우리는 4개 레이어가 전부 순차 의존이라 아직 안 씀(예: 여러 지역 데이터를 병렬 ingest한 뒤 합치는 구조라면 필요) |
| ⚪ `task_a << task_b` | `>>`의 반대 방향 표기 | 기능은 동일, 가독성 때문에 팀 컨벤션에 따라 선택 |

## 5. 알아두면 좋은 것 (아직 안 씀)

| 개념 | 설명 | 비고 |
|---|---|---|
| ⚪ `default_args={"retries": N, "retry_delay": timedelta(...)}` | DAG 전체 태스크에 공통 적용되는 재시도 설정 | 지금 DAG엔 재시도 설정이 없음 — 일시적 네트워크 오류에도 바로 실패 처리됨. `03/파이프라인_설계.md` 8장(개선 여지)에서 다룸 |
| ⚪ `trigger_rule` | 상류 태스크가 실패해도 이 태스크를 실행할지 등의 규칙(`all_success`(기본), `all_failed`, `one_failed` 등) | 예: "silver가 실패해도 알림 태스크는 무조건 실행" 같은 경우에 씀 |
| ⚪ XCom (`ti.xcom_push()` / `ti.xcom_pull()`) | 태스크 사이에 작은 값을 주고받는 메커니즘 | 우리는 태스크 간 데이터 전달을 **S3(MinIO)의 파일 존재 여부**로 암묵적으로 하고 있어서(Bronze가 쓴 걸 Silver가 읽음) XCom이 필요 없음. XCom은 대용량 데이터엔 안 맞고(DB에 직렬화돼 저장됨) 작은 메타데이터(파일 경로, row 수 등) 전달용 |
| ⚪ Sensor (`FileSensor`, `ExternalTaskSensor` 등) | 어떤 조건(파일 생성, 다른 DAG 완료 등)이 될 때까지 대기하는 특수 Operator | 우리는 같은 DAG 안 순차 의존성(`>>`)만으로 충분해서 안 씀 — 여러 DAG에 걸친 의존성이 생기면 필요해짐 |
