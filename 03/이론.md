# 오케스트레이션(Airflow) 이론 정리

`02`(수동 `kubectl run`으로 spark-submit 제출)에서 `03`(Airflow)으로 넘어오면서 정리한 개념들. Spark 자체의 이론(Driver/Executor, 셔플, 조인 전략 등)은 `02/이론.md`, 데이터 레이어링/모델링 설계는 `02/아키텍처.md`에 있음 — 여기는 **"여러 작업의 순서/의존성을 어떻게 자동으로 관리할 것인가"**만 다룬다.

**중요도 기준**
- ★★★ = 실무/면접에서 계속 나오는 핵심 개념
- ★★ = 알아두면 트러블슈팅·설계에 바로 도움 되는 것
- ★ = 심화/참고

---

## 1장. 왜 오케스트레이터가 필요한가 ★★★

`02`까지는 사람이 손으로 순서를 관리했음: `02.py` 제출 → MinIO에서 `_SUCCESS` 확인 → `03.py` 제출. 데이터 파이프라인이 몇 개 안 될 땐 버틸 만하지만, 규모가 커지면 아래 문제가 생김:

- **순서/의존성을 사람이 기억해야 함**: 몇 시에 뭐가 끝났는지, 다음 걸 제출해도 되는지 계속 지켜봐야 함.
- **실패 시 재시도가 수동**: 중간에 죽으면 어디서부터 다시 돌려야 하는지 사람이 판단해야 함.
- **스케줄링이 없음**: "매일 새벽 2시에 자동으로" 같은 요구를 충족 못 함.
- **가시성 부족**: 지금 몇 시간 전 실행이 성공했는지, 평균 소요 시간이 얼마인지 등을 한눈에 볼 방법이 없음.

Airflow(혹은 Argo Workflows, Dagster, Prefect 등)는 이 "순서/의존성/스케줄/재시도/가시성"을 코드(DAG)로 선언하면 대신 관리해주는 도구.

---

## 2장. DAG / Task / Operator ★★★

- **DAG(Directed Acyclic Graph)**: 파이프라인 전체를 나타내는 객체. "방향성 비순환 그래프"라는 이름 그대로, 태스크 사이의 의존성이 순환하면 안 됨(A가 B를 기다리는데 B도 A를 기다리는 구조 불가).
- **Task**: DAG 안의 작업 단위 하나. 우리 DAG의 `ingest_task`, `bronze_task` 등.
- **Operator**: Task가 "무엇을 어떻게 실행할지"를 정의하는 클래스. `KubernetesPodOperator`(팟 하나 실행), `BashOperator`(셸 명령), `PythonOperator`(파이썬 함수) 등 — Task는 Operator의 인스턴스.
- **Task Instance**: 특정 실행 시점(run)에 대한 Task의 실제 실행 기록. 같은 Task라도 매번 새 Task Instance가 생김 — 웹 UI Grid 뷰의 칸 하나하나가 이것.

---

## 2-1장. `02` 방식과의 직접 대응 ★★

| 02(수동) | 03(Airflow) |
|---|---|
| `kubectl run spark-production-pipeline --overrides='{...}'` | `KubernetesPodOperator` |
| 사람이 눈으로 `_SUCCESS` 확인 후 다음 명령 실행 | `task_a >> task_b` (성공해야 다음 실행) |
| 실패하면 사람이 로그 보고 재실행 | (설정하면) 자동 재시도, 실패해도 자동으로 다음 실행 시도 기록됨 |
| 실행 이력이 터미널 스크롤백에만 남음 | 웹 UI에 모든 실행 이력/로그/소요시간이 영구 기록됨 |

즉 Airflow는 마법이 아니라, **우리가 손으로 하던 절차를 그대로 코드로 옮긴 것**(DAG docstring에도 명시). `KubernetesPodOperator`가 "제출자 팟"을 만들고 그 안에서 `spark-submit`이 실제 driver 팟을 다시 만드는 구조는 `02/start.md` 시도7과 동일함.

## 3장. 스케줄링: `start_date` / `schedule` / `catchup` ★★★

가장 헷갈리기 쉬운 3개 개념.

- **`start_date`**: "이 DAG의 스케줄이 언제부터 유효한가"의 하한선. **그 시점에 자동 실행된다는 뜻이 아님.**
- **`schedule`**: 얼마나 자주 실행할지(cron 표현식 또는 `"@daily"` 같은 preset). `None`이면 자동 실행 안 하고 수동 트리거만 가능(우리 DAG의 현재 설정).
- **`catchup`**: `start_date`부터 지금까지 스케줄이 밀린 구간을 전부 소급 실행(backfill)할지 여부. 기본값이 `True`라서, `"@daily"`로 스케줄을 걸어놓고 `start_date`를 한 달 전으로 잡으면 **한 달치가 한꺼번에 몰아서 실행**되는 사고가 날 수 있음 — 그래서 `catchup=False`를 명시적으로 켜두는 게 안전.

**용어 주의 ★**: Airflow의 "실행 시점(execution_date/logical_date)"은 "그 구간의 데이터를 처리한다"는 의미의 논리적 시점이지, 실제로 그 시간에 실행됐다는 뜻이 아님(예: `schedule="@daily"`인 DAG의 2026-08-04 실행은 **2026-08-05 00:00 직후**에 트리거됨 — "하루치가 다 끝난 뒤에 그 하루를 처리"하는 방식). 우리는 `schedule=None`이라 아직 실감할 일이 없지만, 자동 스케줄을 걸면 반드시 부딪히는 개념.

## 4장. Executor: 스케줄러가 태스크를 어떻게 실행시키는가 ★★

Operator가 "태스크 하나가 무엇을 하는지"라면, Executor는 "Airflow 스케줄러 자체가 그 태스크들을 어떤 방식으로 돌리는가"에 대한 훨씬 상위 개념 — **헷갈리기 쉬우니 분리해서 이해할 것**.

| Executor | 방식 | 언제 쓰나 |
|---|---|---|
| SequentialExecutor | 태스크를 한 번에 하나씩만, sqlite DB 사용 | 로컬 학습/테스트 전용(병렬 실행 불가). **우리 `airflow standalone`이 기본으로 이 조합** |
| LocalExecutor | 같은 머신 안에서 여러 태스크를 병렬 프로세스로 실행 | 단일 서버로 충분한 소규모 운영 |
| CeleryExecutor | 여러 워커 머신에 태스크를 분산(메시지 큐 경유) | 태스크 양이 많아 여러 서버로 나눠야 할 때 |
| KubernetesExecutor | 태스크 하나마다 K8s 팟을 새로 띄워서 실행 | 태스크별 리소스 격리/오토스케일링이 필요할 때 |

**`KubernetesPodOperator` vs `KubernetesExecutor` 구분 ★★★** (이름이 비슷해서 자주 혼동):
- `KubernetesPodOperator`는 **Operator**(태스크 하나가 무엇을 하는지) — "이 태스크는 K8s 팟을 만들어서 실행하는 작업이다"라는 뜻. 우리가 쓰는 것.
- `KubernetesExecutor`는 **Executor**(스케줄러 자체의 실행 방식) — "Airflow 스케줄러가 모든 태스크를 K8s 팟으로 실행한다"는 인프라 레벨 설정. 우리는 안 씀(스케줄러 자체는 `airflow-standalone` 컨테이너 안에서 SequentialExecutor로 돎).
- 즉 우리 구조는 "SequentialExecutor로 도는 스케줄러가, 매 태스크마다 `KubernetesPodOperator`를 통해 K8s에 팟 생성을 **요청**하는" 조합. 스케줄러 자체를 K8s화하지 않고도 실제 무거운 작업만 K8s로 격리시킨 절충안.

## 5장. 멱등성(Idempotency)과 재시도 ★★★

- **멱등성**: 같은 태스크를 몇 번 다시 실행해도 결과가 동일해야 한다는 원칙. 오케스트레이터는 실패한 태스크를 재시도시키는 게 기본 동작이라, 태스크가 멱등하지 않으면 재시도할 때마다 데이터가 중복/오염됨.
- 우리 파이프라인이 멱등한 이유: 모든 Spark write가 `mode("overwrite")`라서 몇 번을 다시 실행해도 최종 상태는 동일함(append였다면 재시도할 때마다 데이터가 중복 쌓였을 것).
- `is_delete_operator_pod=True`도 멱등성을 돕는 설정: 재실행 시 이전 팟 이름과 충돌하지 않게 정리해줌.

---

## 6장. 태스크 간 데이터 전달: XCom vs 외부 스토리지 ★★

- **XCom**: Airflow가 제공하는 태스크 간 소통 채널. 작은 값(문자열, 숫자, 짧은 JSON)을 Airflow 메타데이터 DB에 저장해뒀다가 다음 태스크가 꺼내 씀.
- **우리 파이프라인의 실제 방식**: XCom을 전혀 안 씀. Bronze 태스크가 MinIO에 parquet을 쓰고, Silver 태스크는 그 경로(`s3a://test-bucket/bronze/...`)를 **코드에 고정 경로로 알고** 읽음 — 태스크 간 "성공했다"는 신호 자체가 곧 "다음 태스크가 읽을 데이터가 준비됐다"는 의미(`>>` 의존성 하나로 암묵적 해결).
- XCom은 대용량 데이터 전달용이 아님(메타데이터 DB에 직렬화되어 저장되므로) — 우리처럼 기가바이트 단위 데이터를 다루는 파이프라인에선 애초에 선택지가 아니고, S3/데이터 자체가 곧 전달 매개체가 되는 게 정석.

---

## 7장. DAG 파싱과 흔한 실패 모드 ★★

- Airflow 스케줄러는 `dags/` 폴더의 `.py` 파일들을 **주기적으로 다시 읽어들임**(코드를 재배포해도 컨테이너 재시작 없이 반영되는 이유).
- **DAG 파일에 파이썬 문법/임포트 에러가 있으면, 웹 UI 목록에 그 DAG가 아예 안 뜸** — 에러 메시지도 화면 어디에도 안 보여서 "왜 안 보이지?"로 헤맬 수 있음. `airflow dags list-import-errors` CLI로만 원인이 나옴(`03/명령어.md` 참고).
- Jinja 템플릿(`{{ params.x }}`)은 **DAG 파싱 시점이 아니라 태스크 실행(render) 시점**에 치환됨 — 파싱 단계에서 문법 에러가 나는 것과 실행 단계에서 템플릿 값이 잘못되는 것은 별개의 실패 지점이라는 것을 구분해야 디버깅이 빠름.
