## 2026-08-03: 03(Airflow) 스택 구축

### 1. 기존 02 스택을 어떻게 재사용할 것인가

k3s(`k8s-master-node`)와 MinIO(`k8s-s3-minio`)를 03에서 새로 안 띄우고, 02가 만든 **네트워크(`spark_on_kubernetes_cluster_default`)와 볼륨(`spark_on_kubernetes_cluster_k8s-config`)을 `external: true`로 그대로 참조**하는 방식으로 결정. 그래서 03을 띄우기 전에 반드시 02가 먼저 떠 있어야 함.

### 2. kubeconfig가 Airflow 컨테이너에서 그대로 안 먹는 문제

02의 k3s가 만든 kubeconfig(`k3s.yaml`) 안 서버 주소가 `https://127.0.0.1:6443`으로 박혀 있음 — 이건 **k3s 컨테이너 자기 자신 기준 주소**라서, 다른 컨테이너(Airflow)에서 그대로 쓰면 자기 자신의 6443을 찾다가 실패함. (02/start.md 시도7에서 호스트로 kubeconfig를 꺼낼 때 겪은 문제와 같은 종류.)

**해결**: `kubeconfig-prep`이라는 1회성 alpine 컨테이너를 추가해서,
- `127.0.0.1` → `k8s-master-node`(도커 네트워크 안에서 유효한 컨테이너명)로 치환
- 그 컨테이너명에 대한 인증서 SAN이 없어서 `insecure-skip-tls-verify: true`를 주입
- 결과를 공유 볼륨(`kube-config`)에 저장 → Airflow 컨테이너가 `/opt/airflow/kube/config`로 마운트해서 사용

### 3. Airflow 계정을 무작위 대신 고정값으로

`airflow standalone` 단독 실행 시 admin 계정을 매번 무작위로 만듦. `airflow-init`이라는 별도 1회성 컨테이너로 DB 마이그레이션 + `airflow users create`(이미 있으면 실패하지만 그냥 무시) + `airflow users reset-password`(멱등하게 비밀번호 강제 고정)를 먼저 끝내둔 뒤에 `airflow standalone`을 띄우는 공식 quick-start 패턴을 그대로 적용. 계정: `03/.env`의 `_AIRFLOW_WWW_USER_USERNAME`/`_AIRFLOW_WWW_USER_PASSWORD` (현재 admin/1234).

### 4. `KubernetesPodOperator` 프로바이더가 기본 이미지에 없음

`apache/airflow:2.10.3-python3.11` 기본 이미지엔 `apache-airflow-providers-cncf-kubernetes`가 없어서 DAG import 자체가 실패. `_PIP_ADDITIONAL_REQUIREMENTS` 환경변수로 기동 시 설치하도록 처리(02에서 Jupyter 컨테이너가 기동 시 pyspark를 pip install하던 것과 같은 임시방편 — 컨테이너 재생성마다 매번 다시 설치됨, 정식으로는 커스텀 이미지 빌드가 맞음).

### 5. `ingest.py`: Kaggle CLI `--unzip` 옵션이 조용히 실패

`kaggle datasets download --unzip`을 썼더니 exit code는 0(성공)인데 압축이 안 풀려있었음. 원인: `--unzip`은 컨테이너 안에 시스템 `unzip` 바이너리가 있어야 동작하는데, `python:3.11-slim`(Debian slim)엔 없음 — 근데 kaggle CLI가 이 실패를 에러로 처리하지 않고 조용히 넘어감. **해결**: `--unzip` 빼고 zip 그대로 받은 뒤, 표준 라이브러리 `zipfile`로 직접 압축을 풂 (외부 바이너리 의존성 제거).

### 6. RBAC / K8s Secret 사전 준비 (최초 1회)

DAG가 참조하는 `spark` ServiceAccount, `kaggle-credentials`/`minio-credentials` Secret은 DAG 코드가 만들지 않음. k3s에 미리 존재해야 함:

```bash
docker exec -it k8s-master-node kubectl create serviceaccount spark --namespace=default
docker exec -it k8s-master-node kubectl create rolebinding spark-role \
  --clusterrole=edit --serviceaccount=default:spark --namespace=default

docker exec -it k8s-master-node kubectl create secret generic kaggle-credentials \
  --namespace=default \
  --from-literal=username=<KAGGLE_USERNAME> \
  --from-literal=key=<KAGGLE_KEY>

docker exec -it k8s-master-node kubectl create secret generic minio-credentials \
  --namespace=default \
  --from-literal=access-key=minioadmin \
  --from-literal=secret-key=minioadmin
```

이 상태(RBAC + Secret 2개 + `start.py`/`02.py`/`03.py`/`ingest.py`가 code-bucket에 업로드됨)에서 DAG를 트리거해서 ingest → bronze → silver → gold 전체가 한 번 끝까지 성공한 걸 확인함(8/3 저녁).

## 2026-08-04: 4040엔 executor가 뜨는데 Job/Stage가 계속 비어있는 문제

### 증상

DAG를 다시 트리거해서 bronze 태스크가 도는 중, Spark UI(4040)에 접속하면 **executor 2개는 정상적으로 등록**되어 있는데 **Jobs/Stages 탭이 계속 비어있음**. 몇 분을 기다려도 그대로.

### 진단 과정

1. Spark는 lazy evaluation이라 action(`.count()`, `.write()` 등)이 실제로 호출돼야 Jobs 탭에 뭔가 찍힘. executor가 떠서 대기 중인데 job이 하나도 없다는 건 **driver가 action 호출 지점 이전 어딘가에서 멈춰있다**는 뜻으로 판단.
2. `start.py`(bronze 태스크가 돌리는 스크립트)를 열어보니 `spark.read.csv(...)` 직전에 `hadoop_conf.set("fs.s3a.endpoint", "http://172.19.0.3:9000")`으로 **MinIO 엔드포인트를 코드 안에서 하드코딩**하고 있었음.
3. 반면 DAG(`medallion_pipeline.py`)의 `S3A_ENDPOINT`는 이미 `172.19.0.4`로 고쳐져 있었음(이 날 언젠가 수동으로 수정한 흔적, git diff로 확인 — 커밋은 안 된 상태).
4. `docker inspect k8s-s3-minio`로 실제 IP를 재확인 → `172.19.0.4`가 현재 유효한 주소, `172.19.0.3`은 예전(7/31 이전) 주소로 이미 죽어있음.

### 근본 원인

**두 군데(DAG의 `--conf`와 스크립트 내부의 `hadoop_conf.set()`)에서 같은 설정을 서로 다른 값으로 중복 관리**하고 있었음. `hadoop_conf.set()`은 SparkSession이 이미 만들어진 뒤 실행되는 코드라서, spark-submit의 `--conf`로 넘겨준 값을 **스크립트 실행 시점에 다시 덮어써버림**. 그 결과 driver는 죽은 IP(`.3`)로 `spark.read.csv()`를 시도하다가 응답 없이 무한 대기 — executor는 정상 등록됐지만 실제 작업 지시가 한 번도 안 내려간 상태였음.

이 하드코딩은 code-bucket에 업로드된 실제 파일뿐 아니라 로컬 원본(`02/실습코드/01/start.py`, `02.py`, `03.py`)에도 전부 남아있었음(8/3에 `172.19.0.3` → `172.19.0.4` 전환 당시 DAG만 고치고 실행 스크립트 3개는 빠뜨림).

### 해결

1. 로컬 `02/실습코드/01/start.py` / `02.py` / `03.py`의 `172.19.0.3` → `172.19.0.4`로 수정.
2. `boto3` 설치(`pip install boto3`) 후, 고친 3개 파일을 `code-bucket`에 재업로드해서 실제 실행 대상과 로컬 소스를 다시 일치시킴.
3. 재사용 가능하도록 업로드 로직을 `03/upload_to_bucket.py`로 스크립트화 (다음에 또 코드 고치면 이거 한 번 실행하면 됨).
4. 재검증: 업로드 직후 트리거된 bronze 드라이버 로그(`kubectl logs bronze-parquet-job-...-driver`)에서 stage 2.0의 태스크들이 정상적으로 시작/종료되는 것을 확인 — 문제 해결 확인됨.

### 재발 방지 관련 논의 (실무는 어떻게 하는지)

이번 사고의 본질은 "코드가 어디에 있는지(git vs 버킷)가 갈렸고, 같은 설정값이 두 군데(스크립트 내부 하드코딩 vs spark-submit `--conf`)에 중복돼서 한쪽만 고쳐졌던 것". 실무에서 이걸 막는 방법:

- **버킷에 직접 파일을 손으로 올리지 않고, git → CI가 배포**. "지금 버킷에 있는 게 최신인지" 자체를 사람이 신경 쓸 필요가 없어짐.
- **고정 파일명(`start.py`)을 계속 덮어쓰지 않고, 버전/커밋 SHA를 경로에 포함**해서 롤백/추적 가능하게 함.
- **환경별 설정(엔드포인트 등)은 코드에 안 박고 `--conf`/환경변수로만 주입**. 이번 버그의 직접 원인이 바로 이 원칙 위반.

지금 실습 규모에서 전부 도입하긴 과하지만, "설정값 하드코딩 안 하기" 하나는 다음에 `start.py`/`02.py`/`03.py`를 다시 고칠 때 반영할 가치가 있음(아직 미적용 상태로 남겨둠).
