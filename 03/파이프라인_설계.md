# 파이프라인 코드 구조/설계 가이드

`이론.md`가 "Airflow가 뭔지"를 다룬다면, 이 문서는 **"내가 새로 이런 DAG를 짤 때 코드를 어떻게 구조화할 것인가"**에 대한 가이드. `medallion_pipeline.py`를 실제 사례로 삼아, 각 설계 결정을 왜 그렇게 했는지와 함께 정리한다. 인프라 아키텍처(컨테이너 구성, 네트워크)는 `02/아키텍처.md`에 이미 있으므로 여기서는 다루지 않음.

---

## 1장. 설정값은 상수로 위에 모아둔다

```python
KUBE_CONFIG_PATH = "/opt/airflow/kube/config"
NAMESPACE = "default"
SPARK_IMAGE = "apache/spark:3.4.1"
S3A_ENDPOINT = "http://172.19.0.4:9000"
```

DAG 파일 맨 위에 환경/인프라 관련 값을 상수로 몰아두면, 바뀔 때 "코드 전체에서 이 값을 쓰는 곳을 다 찾아서 고치는" 대신 **선언부 한 줄만 고치면** 모든 태스크에 반영됨.

**한계 (8/4 실제로 겪은 문제)**: 이 상수는 DAG 파일 안에서는 한 곳이지만, `start.py`/`02.py`/`03.py`(code-bucket에 별도로 올라가는 실행 스크립트)에도 **같은 값이 각자 하드코딩**되어 있었음. DAG의 `S3A_ENDPOINT`만 고치고 저 세 파일을 빠뜨려서 "설정값이 여러 파일에 흩어져 있으면 한쪽만 고치는 실수가 난다"는 걸 직접 겪음(`03/시행착오_0803-0804.md` 참고). 근본적인 해결은 이런 값을 코드에 아예 안 박고 Airflow `Variable`/`Connection`이나 spark-submit `--conf`로만 주입하는 것 — 지금은 학습 단계라 상수로 남겨뒀지만, 파일이 여러 개로 늘어나면 반드시 손봐야 할 지점(8장 참고).

## 2장. 반복되는 설정은 리스트로 뽑고, 태스크 생성은 함수로 팩토리화한다

```python
COMMON_CONF = [
    "--conf", f"spark.kubernetes.container.image={SPARK_IMAGE}",
    "--conf", "spark.dynamicAllocation.enabled=true",
    # ... 15개 이상의 --conf
]

def spark_submit_args(job_name: str, script_path: str) -> list[str]:
    return ["--master", "...", "--deploy-mode", "cluster", "--name", job_name, *COMMON_CONF, script_path]

def make_task(task_id: str, job_name: str, script_path: str) -> KubernetesPodOperator:
    return KubernetesPodOperator(task_id=task_id, name=job_name, ..., arguments=spark_submit_args(job_name, script_path), ...)
```

`bronze_task`/`silver_task`/`gold_task` 세 태스크는 **스크립트 경로 하나만 다르고 나머지 설정(이미지, 리소스 제한, S3 접속 정보 등)은 완전히 동일**함. 이걸 세 번 복붙하지 않고 `make_task()` 함수 하나로 뽑아내면:
- 리소스 제한값(`spark.executor.memory=1g` 등, `02/start.md` 11-2에서 크래시 겪고 얻은 값)을 한 곳만 고치면 세 태스크에 다 반영됨.
- 새 레이어(예: `platinum_task`)를 추가할 때 `make_task("platinum_stats", "platinum-job", "s3a://code-bucket/04.py")` 한 줄이면 끝.

**설계 원칙**: 태스크 사이에 "달라지는 부분"과 "똑같은 부분"이 보이면, 똑같은 부분을 먼저 함수/상수로 뽑아내고 달라지는 부분만 인자로 받게 만든다(DRY).

## 3장. 태스크 단위를 어떻게 쪼갤 것인가

- **원칙: 레이어(Bronze/Silver/Gold) = 태스크 경계.** 하나의 스크립트에 다 합치지 않은 이유는 `02/start.md` 15장(실무 참고)에 이미 정리된 것과 동일: Gold 로직만 고쳐도 무거운 Bronze/Silver부터 매번 재실행할 필요가 없고, 중간 실패 시 그 레이어부터만 재시작 가능하며, 같은 Silver 결과를 여러 Gold job이 재사용할 수 있는 구조가 됨.
- **`ingest_task`를 별도로 뺀 이유**: Kaggle API 호출은 Spark 연산과 성격이 다름(외부 서비스 의존, 실패 사유가 다름 — 네트워크/인증 문제 vs 연산 리소스 문제). 이미지도 `python:3.11-slim`으로 Spark 이미지(`apache/spark:3.4.1`)와 다르고, 리소스도 훨씬 가벼움(`container_resources`로 별도 제한). 성격이 다른 작업은 같은 태스크에 억지로 합치지 않고 분리하는 게 원칙.
- **판단 기준 정리**: "이 작업이 독립적으로 재시작될 필요가 있는가?", "리소스/이미지 요구사항이 다른가?", "실패 원인의 성격이 다른가?" 중 하나라도 해당하면 별도 태스크로 쪼갠다.

## 4장. 파라미터화: "실행마다 바뀌는 값"과 "고정값" 구분

```python
params={"kaggle_file": "2019-Oct.csv"}   # 실행마다 바뀔 수 있는 값
...
"KAGGLE_FILE": "{{ params.kaggle_file }}"  # 실행 시점에 주입
```

DAG `params`로 노출한 값은 딱 하나, `kaggle_file`뿐임. `S3A_ENDPOINT`나 `SPARK_IMAGE` 같은 값은 params가 아니라 1장의 상수로 뒀음 — 기준은 "**이 값을 트리거할 때마다 바꾸고 싶은가, 아니면 인프라가 바뀔 때만 바뀌는가**". 전자는 params(사용자가 매번 조정하는 다이얼), 후자는 코드 상수(운영자가 가끔 고치는 설정)로 나누면 웹 UI에서 실행할 때 신경 써야 할 값이 최소화됨.

## 5장. 자격증명은 코드에 절대 안 적고 흐름만 연결한다

```
03/.env (KAGGLE_USERNAME, KAGGLE_KEY)
  → docker-compose.yml 환경변수로 airflow 컨테이너에 주입
  → ingest_task의 env_vars/secrets로 K8s 팟에 재주입
  → ingest.py 안에서 os.environ으로 읽음
```

DAG 코드(`medallion_pipeline.py`) 어디에도 실제 kaggle 키나 minio 비밀번호 문자열이 없음 — `Secret("env", "KAGGLE_USERNAME", "kaggle-credentials", "username")`처럼 **"K8s Secret의 어느 키를 어느 환경변수로 매핑할지"만** 선언되어 있고, 실제 값은 `kubectl create secret`으로 클러스터에만 존재함. 코드가 git에 커밋되거나 다른 사람에게 공유돼도 자격증명은 안 새어나감 — 이 흐름을 유지하는 게 원칙(값을 "코드에 안 적기"가 아니라 "값의 출처를 한 군데(K8s Secret)로만 고정하기"가 핵심).

## 6장. 멱등성 있게 태스크를 짠다

- 모든 Spark write가 `mode("overwrite")`: 같은 태스크를 몇 번 재실행해도 최종 결과가 동일함(append였다면 재시도마다 데이터가 중복 쌓였을 것).
- `is_delete_operator_pod=True`: 재실행 시 이전 팟이 남아있어서 이름이 충돌하는 일을 방지.
- **설계 시 자문할 질문**: "이 태스크가 실패해서 Airflow가 자동으로/사람이 수동으로 다시 실행시켰을 때, 데이터가 두 번 쌓이거나 꼬이지 않는가?" 아니라면 멱등하게 고쳐야 재시도 기능을 안전하게 켤 수 있음.

## 7장. 부트스트랩 스크립트 패턴 (`INGEST_BOOTSTRAP`)

```python
INGEST_BOOTSTRAP = """
pip install --quiet --no-cache-dir boto3 kaggle
python3 -c "... s3.download_file('code-bucket', 'ingest.py', '/tmp/ingest.py') ..."
python3 /tmp/ingest.py
"""
```

`ingest_task`는 이미지(`python:3.11-slim`)에 실제 로직을 굽지 않고, 팟이 뜨자마자 **부트스트랩 코드(인라인)로 진짜 로직(`ingest.py`)을 code-bucket에서 받아와 실행**함. `start.py`/`02.py`/`03.py`가 code-bucket에서 spark-submit 대상 경로로 참조되는 것과 같은 패턴.

**왜 이렇게 하나**: 이미지를 커스텀 빌드해서 코드를 굽는 게 정석이지만(지난 대화의 "실무는 어떻게" 참고), 그러면 로직 한 줄 고칠 때마다 이미지를 다시 빌드·푸시해야 해서 학습 단계에서는 번거로움. 대신 **범용 이미지 + 실행 시점에 최신 코드 받기**로 타협 — 이미지 재빌드 없이 코드만 고치고 재업로드(`03/upload_to_bucket.py`)하면 바로 다음 실행에 반영됨. 단, 이 타협의 대가가 바로 8장의 한계.

## 8장. 지금 설계의 한계와 다음 개선 여지

지금 구조는 "학습 단계에서 손으로 확인 가능한 만큼만" 단순하게 짠 것. 실무로 넘어가려면 아래를 순서대로 고려해야 함:

| 현재 상태 | 문제 | 개선 방향 |
|---|---|---|
| 설정값(엔드포인트 등)이 DAG + 스크립트 3개에 각각 하드코딩 | 한쪽만 고치는 실수(8/4에 실제 발생) | Airflow `Variable`/`Connection`으로 단일화하거나, 최소한 스크립트가 `--conf`로 받은 값만 쓰고 자체 하드코딩을 없애기 |
| 이미지에 코드를 안 굽고 매번 code-bucket에서 받아옴 | "지금 버킷에 있는 게 최신 버전인지" 사람이 신경 써야 함, 버전 추적/롤백 불가 | CI가 커밋마다 코드를 빌드해서 버전 태그가 붙은 경로(`.../v1.2.3/start.py`)나 Docker 이미지로 배포 |
| `retries`/`retry_delay` 미설정 | 일시적 네트워크 오류에도 바로 실패 처리 | `default_args`에 재시도 정책 추가(단, 멱등성이 보장돼야 안전하게 켤 수 있음 — 6장) |
| `_PIP_ADDITIONAL_REQUIREMENTS`로 컨테이너 기동 시마다 provider 재설치 | 기동이 느려짐, 네트워크 장애 시 Airflow 자체가 못 뜸 | provider가 이미 설치된 커스텀 Airflow 이미지를 빌드 |
| SequentialExecutor + sqlite | 태스크가 늘어나면 병렬 실행이 안 돼서 병목 | 태스크 양이 늘면 LocalExecutor(+PostgreSQL)나 CeleryExecutor/KubernetesExecutor로 전환 |
| XCom/Sensor 안 씀 | 지금은 단순 순차라 문제 없지만, 여러 DAG에 걸친 의존성이나 외부 이벤트 대기가 필요해지면 한계 | `ExternalTaskSensor`, 소규모 메타데이터는 XCom으로 확장 |

지금 단계에서 전부 적용할 필요는 없지만, "왜 아직 안 했는지"를 알고 있는 것과 모르고 넘어가는 것은 다름 — 다음에 파이프라인을 더 키울 때 이 표부터 다시 볼 것.
