# Spark 이론 정리

Airflow로 넘어가기 전에 지금까지 실습(00~02)에서 몸으로 부딪힌 것들을 이론적으로 다시 묶은 문서. 비슷한 주제끼리 챕터로 나누고, 각 챕터/항목에 중요도를 표시했다.

**중요도 기준**
- ★★★ = 실무/면접에서 계속 나오는 핵심 개념. 반드시 설명 가능해야 함
- ★★ = 알아두면 트러블슈팅·설계에 바로 도움 되는 것
- ★ = 심화/참고. 필요할 때 찾아보면 되는 것

> 데이터 레이크/웨어하우스 설계 아키텍처(메달리온 포함, Lambda/Kappa/Data Mesh 등)는 별도로 [`아키텍처.md`](./아키텍처.md)에 정리했다.

---

## 1장. Spark란 무엇인가 ★★

- Spark는 **분산 인메모리 연산 엔진**. Hadoop MapReduce가 매 단계마다 디스크에 중간 결과를 쓰는 것과 달리, 가능한 한 메모리에서 파이프라인을 이어가서 반복 연산(머신러닝, 반복 쿼리)이 훨씬 빠름.
- MapReduce 개념(map → shuffle → reduce)은 Spark 안에도 그대로 살아있음 — `reduceByKey` 실습에서 짠 `flatMap → map → reduceByKey`가 바로 고전 워드카운트 MapReduce 패턴.
- Spark SQL, DataFrame/Dataset, MLlib(머신러닝), GraphX(그래프), Structured Streaming(스트리밍)까지 하나의 엔진 위에서 통합 제공 — "여러 종류의 데이터 작업을 하나의 클러스터·하나의 API 스타일로" 처리하는 게 핵심 가치.

---

## 2장. 아키텍처: Driver / Executor / Cluster Manager ★★★

- **Driver**: 사용자 코드가 실제로 실행되는 프로세스. SparkContext/SparkSession이 여기서 생성됨. 실행 계획(DAG)을 짜고, Task를 Executor들에게 나눠주고, 최종 결과(`collect()` 등)를 돌려받는 "지휘관" 역할.
- **Executor**: 실제 Task를 실행하는 워커 프로세스. Driver가 지시한 연산을 자기 파티션 데이터에 대해 수행하고 결과를 Driver나 다른 Executor로 보냄. 하나의 애플리케이션 실행 동안 계속 떠 있으면서 여러 Task를 순차/병렬로 처리.
- **Cluster Manager**: Executor를 어디에, 몇 개나 띄울지 결정하는 리소스 관리자. Standalone(Spark 자체 매니저) / YARN / Kubernetes / Mesos 중 선택 가능 — 우리는 로컬(00,01)에서는 Standalone/local, `02`에서는 Kubernetes를 씀.
- **Job → Stage → Task 계층 구조**:
  - **Job**: Action 하나(`.show()`, `.count()` 등)가 트리거하는 전체 작업 단위.
  - **Stage**: Job 안에서 셔플 경계로 나뉘는 구간. 셔플이 없으면 Stage 하나, 셔플이 있는 연산(`groupBy`, `join` 등)이 나올 때마다 Stage가 새로 쪼개짐.
  - **Task**: Stage 안에서 파티션 하나를 처리하는 최소 실행 단위. Executor의 코어 하나가 Task 하나를 담당(파티션 개수만큼 Task 개수가 생김).

## 3장. 실행 모델: Lazy Evaluation과 DAG ★★★

- **Transformation vs Action**: Transformation(`map`, `filter`, `select`, `join`, `groupBy` 등)은 "계획"만 세우고 실제 연산은 안 함. Action(`collect`, `count`, `show`, `write` 등)을 만나야 그제서야 지금까지 쌓인 계획 전체가 실행됨(Lazy Evaluation).
  - 왜 이렇게 설계했나: 미리 전체 계획을 다 본 다음 실행하기 때문에, Catalyst 옵티마이저가 불필요한 단계를 합치거나 순서를 바꾸는 등 **전역 최적화**를 할 수 있음. 즉시 실행(eager)이었다면 이런 최적화 여지가 없음.
- **RDD Lineage(계보)**: Transformation이 적용되는 순서를 나타내는 DAG(방향성 비순환 그래프). 어떤 파티션이 메모리에서 유실돼도, 이 lineage를 따라 원본부터 다시 계산해서 복구 가능 — Spark의 장애 허용성의 근본 원리(13장 참고).
- **초보자가 흔히 하는 실수(캐싱 없이 반복 사용)**: 정제된 DataFrame을 여러 Action에서 재사용하면, 캐싱을 안 해뒀을 경우 Spark는 매번 원본부터 처음 계획을 전부 다시 실행함. `.cache()`로 "이 지점까지 계산한 결과는 메모리에 붙여놔"라고 명시해야 재계산을 막을 수 있음(9장 참고).

## 4장. RDD vs DataFrame vs Dataset ★★★

| | RDD | DataFrame | Dataset |
|---|---|---|---|
| 추상화 수준 | 가장 로우레벨(그냥 분산 객체 컬렉션) | 스키마가 있는 테이블(row/column) | DataFrame + 타입 안정성(주로 Scala/Java) |
| 최적화 | Catalyst의 도움을 못 받음(블랙박스 람다) | Catalyst/Tungsten이 실행계획을 최적화 | DataFrame과 동일 |
| API 스타일 | `map`/`flatMap`/`reduceByKey` 같은 함수형 | `select`/`filter`/`groupBy`처럼 SQL스러운 API | DataFrame + 컴파일 타임 타입 체크 |
| 언제 쓰나 | 스키마가 없는 비정형 데이터, 세밀한 저수준 제어가 필요할 때 | 대부분의 실무 배치/SQL 작업 (기본 선택지) | PySpark에서는 사실상 잘 안 씀(파이썬은 동적 타입이라 Dataset의 이점이 적음) |

- 실습에서 워드카운트는 RDD(`flatMap`/`map`/`reduceByKey`)로, 이후 실무형 파이프라인(Bronze/Silver/Gold)은 전부 DataFrame으로 짠 이유가 바로 이 표 — 구조화된 대용량 데이터는 DataFrame이 압도적으로 유리(옵티마이저 혜택).

## 5장. 파티션과 셔플 ★★★

- **파티션**: 데이터를 여러 Executor에 나눠서 병렬 처리하기 위한 조각 단위. `df.rdd.getNumPartitions()`로 확인 가능.
- **셔플이란**: 특정 연산(`groupBy`, `join`(브로드캐스트 아닌 경우), `distinct`, `repartition`, `orderBy` 등)을 위해 여러 파티션에 흩어진 데이터를 키 기준으로 네트워크를 통해 재배치하는 것. `local[*]` 모드에서도 실제로 로컬 디스크(`/tmp/spark-*`, `/tmp/blockmgr-*`)에 임시 파일을 쓰고 읽는 방식으로 동일하게 발생함(네트워크 대신 로컬 I/O일 뿐).
- **셔플이 느린 이유**: 네트워크 전송 + 디스크 임시 저장(spill)이 동시에 일어나는 구간이라 Spark 연산 중 병목의 8~9할을 차지. "어떻게 하면 셔플을 최소화할까"가 튜닝의 핵심 화두.
- **셔플 안 일어나는 연산**: `map`, `filter`, `select`, `withColumn` — 자기 파티션 안의 데이터만 보면 됨.
- **셔플 일어나는 연산**: `groupBy`/`reduceByKey`, `distinct`/`dropDuplicates`, `join`(브로드캐스트 아닌 경우), `repartition(col)`, `orderBy`.
- **저장 시 파티션 개수와 파일 개수의 관계 ★★**: `.write().partitionBy(col)`은 컬럼 값별로 **폴더**를 나누는 것(폴더 개수 = 그 컬럼의 고유값 개수)이고, **폴더 안 파일 개수는 저장 시점의 실행 파티션 개수**에 따라 결정됨. 실행 파티션이 여러 개인 채로 `partitionBy`를 하면 폴더마다 파일이 여러 개(최대 파티션 개수만큼) 생기는 "small file 문제"가 생김 — 이걸 우리는 `repartition(파티션컬럼)`으로 폴더당 파일 1개로 줄여서 커밋 시간을 20분 → 4분 42초로 줄임 (파일 개수 3014 → 130).
- **`repartition` vs `coalesce` ★★★**:
  - `repartition(n)` / `repartition(col)`: 셔플을 일으켜서 **완전히 새로** 파티션을 나눔. 늘리기/줄이기 둘 다 가능하고, 특정 컬럼 기준으로 나누면 "같은 값은 반드시 같은 파티션"을 보장.
  - `coalesce(n)`: 셔플 없이 이웃 파티션끼리 합쳐서 개수만 줄임. 저렴하지만 "같은 키를 한 곳에 모아준다"는 보장이 없음. 이미 작은 결과(Gold 집계 테이블처럼 수십~수백 행)를 파일 1개로 정리할 때 적합.
- **AQE(Adaptive Query Execution) ★★**: 실행 도중 실제 데이터 크기를 보고 셔플 파티션 개수를 자동으로 줄여주는 최적화(Spark 3.0+ 기본 활성화인 경우 많음). 우리 실습에서 기본 200개 셔플 파티션을 실제 데이터(263MiB) 기준 10개로 자동 축소해준 사례.

## 6장. 조인 전략 ★★★

- **Shuffle(Sort Merge) Join**: 기본 join 방식. 양쪽 테이블 모두 join key 기준으로 셔플해서 같은 키를 같은 파티션에 모은 뒤 정렬-병합. 양쪽 다 크면 이 방식 외엔 선택지가 없음.
- **Broadcast Hash Join ★★★**: 한쪽 테이블이 충분히 작으면(기본 임계치 약 10MB, `spark.sql.autoBroadcastJoinThreshold`로 조절) 그 작은 테이블 전체를 모든 Executor에 복사해서, 큰 쪽 테이블은 전혀 이동시키지 않고 로컬에서 join. **셔플이 없어서 훨씬 빠름**. `sf.broadcast(df)`로 명시적으로 강제할 수도 있음 — self-join row 폭발 버그를 고칠 때 이 방식으로 조인 3번을 셔플 없이 처리함.
- **자동 브로드캐스트의 함정 ★**: 큰 데이터인데 통계 정보가 부실해서 옵티마이저가 "작다"고 착각하면 브로드캐스트하다가 Executor OOM 발생 가능 — 데이터 크기를 확신할 수 있을 때만 명시적으로 `broadcast()` 힌트를 주는 게 안전.
- **셀프 조인(Self Join) 시 카디널리티 폭발 주의 ★★★**: 조인 키가 1:1이 아닌 상태에서 OR 조건(`(a==b) | (c==d)`)으로 조인하면 다대다 매칭이 일어나 행 수가 기하급수적으로 불어날 수 있음(우리 실습에서 10만 행 → 2600만 행). 해결책은 조회표를 "키 하나당 값 하나"로 정규화(`dropDuplicates`)한 뒤, OR 하나로 묶지 않고 **키 컬럼별로 순차 조인 + `coalesce`로 값 병합**.

## 7장. Catalyst Optimizer & Tungsten & AQE ★★

- **Catalyst Optimizer**: DataFrame/SQL 코드를 실행하기 전, 논리적 실행계획을 분석해서 필터를 최대한 먼저 적용(Predicate Pushdown), 안 쓰는 컬럼 제거(Column Pruning), 상수 계산 미리 처리 등으로 **더 효율적인 물리적 실행계획**으로 바꿔주는 규칙 기반+비용 기반 최적화기.
- **DataFrame API와 SQL이 성능 차이가 없는 이유**: 둘 다 결국 Catalyst가 이해하는 동일한 논리적 실행계획으로 변환되기 때문. `createOrReplaceTempView` + `spark.sql(...)`로 짠 쿼리와 DataFrame 메서드 체이닝으로 짠 코드가 최종적으로 같은 물리 실행계획이 될 수 있음.
- **Tungsten**: JVM 객체 대신 바이트 배열 기반의 자체 메모리 레이아웃(off-heap 포함)을 써서 GC 오버헤드와 직렬화 비용을 줄이는 실행 엔진 최적화(Catalyst가 짠 계획을 더 빠르게 물리적으로 수행하게 해주는 하부 계층).
- **`explain(True)`로 실행계획 읽기 ★★**: 논리 계획(Parsed → Analyzed → Optimized)과 물리 계획을 전부 출력. 물리 계획에 `Exchange hashpartitioning(...)`이 보이면 그 지점에서 셔플이 확정적으로 발생한다는 뜻 — 코드만 보고 셔플 여부를 추측하는 대신 이걸로 직접 확인하는 습관이 중요.

## 8장. 메모리 관리 ★★

- Executor 메모리는 크게 **Execution Memory**(셔플/조인/정렬/집계용 임시 연산 공간)와 **Storage Memory**(`cache()`/`persist()`로 올려둔 데이터)로 나뉘고, Spark 1.6+부터는 이 둘이 필요에 따라 서로 경계를 유동적으로 빌려쓰는 **Unified Memory Management** 방식.
- `spark.executor.memory`: JVM 힙 메모리. `spark.executor.memoryOverhead`: 힙 밖에서 쓰는 메모리(네이티브 라이브러리, 프로세스 오버헤드 등) — 이번 실습에서 8GB 예산 안에 맞추려고 `executor.memory=1g` + `memoryOverhead=512m`로 명시 제한.
- **Spill(스필)**: 연산에 필요한 데이터가 할당된 메모리를 초과하면 디스크로 밀어내는(spill) 현상. 셔플 중 메모리 부족의 대표적 증상이고, 심해지면 성능이 급격히 나빠짐 — Spark UI의 Stage 상세 화면에서 Spill 지표로 확인 가능.

## 9장. 캐싱과 영속화 ★★

- `cache()` = `persist(StorageLevel.MEMORY_AND_DISK)`의 축약형. 메모리가 부족하면 자동으로 디스크로 넘어감(기본값이 이미 안전한 조합).
- **StorageLevel 종류 ★**: `MEMORY_ONLY`(빠르지만 메모리 부족 시 유실) / `MEMORY_AND_DISK`(기본, 안전) / `DISK_ONLY` / `_SER`(직렬화해서 저장, 메모리 절약하지만 CPU 비용) / `_2`(다른 노드에 복제본 하나 더, 장애 대비).
- 캐싱은 **Transformation**이라 그 자체로는 실행 안 됨 — 다음 Action이 실행되는 시점에 계산과 동시에 캐싱이 이루어짐. 캐싱해도 한 번도 Action이 안 불리면 아무 일도 안 일어남.
- 다 쓴 캐시는 `unpersist()`로 명시적으로 해제하는 게 좋음(메모리 압박 상황에서는 LRU로 자동 축출되긴 하지만, 명시적 해제가 더 예측 가능).

## 10장. 클러스터 매니저와 배포 모드 ★★★

- **Cluster Manager 종류**: Standalone(우리 `01` 실습의 `spark://jupyter:7077`), YARN(하둡 생태계 표준), **Kubernetes**(우리 `02` 실습), Mesos(요즘은 잘 안 씀).
- **Deploy Mode: client vs cluster ★★★**
  - `client`: Driver가 `spark-submit`을 실행한 그 프로세스(우리의 경우 Jupyter 컨테이너) 안에서 돎. 대화형 개발(Jupyter, 로컬 디버깅)에 적합.
  - `cluster`: Driver 자체도 클러스터 안의 별도 팟/컨테이너로 생성됨. 운영 배포용 — Jupyter 컨테이너가 죽어도 job은 영향 없음.
  - k8s에서 `client` 모드를 시도했을 때 겪은 문제(시도 1): Driver가 Jupyter 컨테이너 안에 있고, k8s가 만든 Executor 팟들이 그 Driver에게 **역으로 접속**해야 해서 `spark.driver.host`/`port` 고정, 네트워크 도달성 등 추가로 풀어야 할 문제가 생김 — 그래서 cluster 모드로 전환.
- **로컬(`local[*]`) 모드는 클러스터 매니저를 아예 안 씀 ★★★**: Jupyter 컨테이너 안 JVM 하나가 로컬 CPU 코어 수만큼 스레드를 만들어 Driver와 Executor 역할을 전부 혼자 처리. 팟도 생성 안 됨 — 코드 개발/디버깅/작은 결과 확인에 적합, 대용량 처리에는 부적합.

## 11장. Kubernetes 위의 Spark 심화 ★★★

- **Driver가 Executor를 직접 만든다**: Spark on Kubernetes는 Driver 팟이 Kubernetes API를 직접 호출해서 Executor 팟을 동적으로 생성/삭제함. 그래서 Driver의 ServiceAccount에 **팟을 생성할 RBAC 권한**이 반드시 있어야 함(`clusterrole=edit` 등) — 없으면 `Forbidden: cannot create pods` 에러.
- **submitter 팟과 driver 팟은 별개 ★★**: `kubectl run`으로 띄우는 팟은 `spark-submit`을 실행하는 "제출자" 팟일 뿐이고, `--deploy-mode cluster`는 그 안에서 다시 **새로운 driver 팟**을 만듦. 그래서 driver 팟에 쓸 이미지는 submitter의 `--image`가 아니라 `spark.kubernetes.container.image` conf로 별도 지정해야 함.
- **동적 할당(Dynamic Allocation)**: 고정 `executor.instances` 대신 `dynamicAllocation.enabled=true` + `minExecutors`/`maxExecutors`로 부하에 따라 Executor 개수를 자동 조절. `shuffleTracking.enabled=true`가 필수인 이유: k8s에는 YARN의 External Shuffle Service가 없어서, 이게 없으면 idle Executor가 회수될 때 그 Executor가 들고 있던 셔플 데이터가 통째로 유실되어 재계산이 발생함.
- **컨테이너 네트워크 vs 팟 네트워크는 다른 세계 ★★★**: 도커 컴포즈 안의 컨테이너들은 도커 임베디드 DNS(예: `minio-storage`)로 서로를 찾지만, k3s가 만드는 팟들은 **별도의 팟 네트워크**에 있어서 그 DNS가 안 먹힘 — 이번 실습에서 실제 겪은 문제. 해결책은 IP를 직접 알아내서(`docker inspect`) 쓰거나, 제대로 하려면 k8s 서비스 디스커버리(ClusterIP Service)로 양쪽을 이어주는 것.
- **자격증명은 실행 "전"에 필요 ★★**: `spark-submit`이 실행할 스크립트 파일 자체를 원격(S3 등)에서 내려받는 과정은 파이썬 코드가 시작되기도 전에 일어나는 단계라, 스크립트 안의 `hadoop_conf.set(...)`으로는 그 다운로드 자체에 자격증명을 줄 수 없음 — `spark-submit --conf`로 미리 넘겨야 함.

## 12장. 파일 포맷과 스토리지 ★★★

- **CSV vs Parquet**:
  - CSV: 행 기반(row-oriented), 텍스트, 스키마 없음. `inferSchema=True`는 타입 추론을 위해 파일을 미리 한 번 훑어야 해서 대용량에서 느림.
  - Parquet: **컬럼 기반(columnar)** 저장, 스키마가 파일에 내장, 컬럼 단위 압축·인코딩. 특정 컬럼만 읽는 쿼리(`select` 일부 컬럼)에서 훨씬 빠르고, 압축률도 좋음(우리 데이터 8.4GiB → 2.3GiB). 대부분의 배치 파이프라인에서 중간/최종 저장 포맷의 기본 선택지.
- **오브젝트 스토리지(S3/MinIO)와 S3A 커넥터 ★★**: `s3a://` 스킴은 Hadoop의 S3A 파일시스템 구현을 통해 S3 호환 오브젝트 스토리지를 HDFS처럼 다루게 해줌. `spark.jars.packages`로 `hadoop-aws`/`aws-java-sdk-bundle`을 추가해야 하고, **반드시 세션(SparkContext) 생성 전**에 지정해야 classpath에 반영됨.
- **Small File 문제 ★★★**: 오브젝트 스토리지는 파일 수가 많을수록(특히 `rename`이 실제로는 copy+delete로 구현되는 S3A 특성상) 커밋 단계가 느려짐. 5장에서 다룬 `repartition(파티션컬럼)`이 이 문제의 표준 해법.
- **버킷의 논리적 성격 ★**: 버킷은 물리 저장소를 논리적으로 묶은 이름공간일 뿐, 실제로는 경로 설정을 통해 여러 물리 저장소에 걸쳐 저장될 수도 있음 — 버킷 = 디스크 파티션이 아니라는 것.

## 13장. 장애 허용성(Fault Tolerance) ★★

- **RDD Lineage 기반 복구 ★★**: 어떤 파티션이 메모리/디스크에서 유실돼도, 그 파티션을 만들어낸 Transformation 계보(lineage)를 따라 원본 데이터부터 다시 계산해서 복구. 별도의 복제(replication) 없이도 장애를 견딜 수 있는 Spark의 핵심 설계.
- **Task 재시도 ★**: 특정 Task가 Executor 장애 등으로 실패하면 Spark가 자동으로 다른 Executor에서 재시도(`spark.task.maxFailures`로 최대 횟수 조절). 계속 실패하면 Stage/Job 전체가 실패 처리됨.
- **Speculative Execution ★**: 유난히 느린(straggler) Task를 감지하면 다른 Executor에서 동일한 Task를 하나 더 띄워서 먼저 끝나는 쪽을 채택하는 기능(`spark.speculation`). 데이터 skew나 특정 노드 성능 저하로 인한 지연을 완화.
- **Checkpoint ★**: 매우 긴 lineage(반복 연산 등)는 복구 시 처음부터 전부 재계산해야 해서 비효율적일 수 있음 — `checkpoint()`로 특정 시점의 데이터를 안정적인 스토리지(HDFS/S3)에 실제로 써서 lineage를 끊고 그 지점부터 복구하게 만듦. `cache()`는 메모리 위주(유실 가능), `checkpoint()`는 안정적 스토리지(유실 안 됨)라는 점이 다름.

## 14장. 모니터링/디버깅 ★★

- **Spark UI(4040) 주요 탭 ★★**: Jobs(Action 단위 진행 상황) / Stages(셔플 경계로 나뉜 구간별 상세, Spill 지표 포함) / Storage(캐싱된 데이터 현황) / Environment(적용된 설정값 전체 확인 — `.config()`가 실제로 반영됐는지 검증할 때 유용) / SQL(DataFrame/SQL 쿼리별 실행계획 시각화).
- **History Server(18080)**: 종료된(또는 진행 중인) job의 event log를 영구 스토리지에서 읽어서 재생해주는 상시 서비스. `spark.eventLog.enabled=true` + `spark.eventLog.dir`를 켠 job만 여기 나타남. 실시간 진행률(progress bar)은 안 보이고 완료된 stage/task 통계 위주 — "지금 도는지"는 여전히 개별 driver의 4040이 필요.
- **실행계획을 코드로 확인하는 습관 ★★**: `df.explain(True)`로 셔플 여부·조인 전략을 직접 눈으로 확인하는 게, 감으로 "이건 느릴 것 같다"고 추측하는 것보다 훨씬 정확함.

## 15장. 다음 단계 예습 — 오케스트레이션과 Airflow ★★★

- 지금까지는 "`02.py` 제출 → MinIO에서 `_SUCCESS` 확인 → `03.py` 제출"을 전부 손으로 순서 관리했음. 실무에서는 이 순서/의존성 관리를 **오케스트레이터**가 대신함(Airflow, Argo Workflows, Databricks Workflows 등).
- **DAG(Directed Acyclic Graph)**: Airflow에서 태스크 간 실행 순서/의존성을 정의하는 단위. Spark의 실행 DAG(3장)와 이름은 같지만 레벨이 다름 — Airflow의 DAG는 "job들 사이의" 순서(예: `bronze_task >> silver_task >> gold_task`), Spark의 DAG는 "한 job 안 연산들 사이의" 순서.
- **`_SUCCESS` 마커 파일의 역할 ★★**: 우리가 매번 눈으로 확인했던 이 파일이, 오케스트레이터 입장에서는 "이전 태스크가 정상적으로 끝났다"를 판단하는 핵심 신호가 됨(Sensor가 이 파일의 존재를 감시하는 식으로 구현되기도 함).
- **`KubernetesPodOperator` ★★★**: Airflow가 Kubernetes 위에서 태스크를 실행할 때 쓰는 Operator. 우리가 `kubectl run`으로 손으로 submitter 팟을 만들던 것을, Airflow가 태스크 실행 시점마다 자동으로 만들어주는 것과 같은 개념 — 지금 익힌 `kubectl get/logs/describe`로 팟 상태 확인하는 루틴이 Airflow 도입 후에도 디버깅에 그대로 필요함.
- **재시도/스케줄링 개념**: Airflow는 태스크별 재시도 횟수, 재시도 간격, 실패 알림, cron 기반 스케줄링(`schedule_interval`) 등을 선언적으로 관리 — Spark의 Task 재시도(13장)와는 다른 레벨(job 전체 단위)의 재시도라는 점을 구분해서 이해할 것.
