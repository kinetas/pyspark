## 1. Docker Compose / 컨테이너 관리

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `docker compose up` | `docker-compose.yml`에 정의된 컨테이너들을 기동 | `-d`를 안 붙이면 포그라운드로 로그가 계속 출력됨 |
| ⚪ `docker compose up -d` | 백그라운드로 기동 | 터미널을 계속 붙잡고 있고 싶지 않을 때 |
| ⚪ `docker compose down` | 컴포즈로 띄운 컨테이너/네트워크를 전부 정리 | **주의**: `k8s-master-node`가 재생성되면 k3s 내부 상태(RBAC, Deployment 등)가 전부 초기화됨. 볼륨 마운트된 MinIO 데이터는 살아남음 |
| 🔵 `docker exec -it <컨테이너명> bash` / `sh` | 실행 중인 컨테이너 안으로 들어가 셸 실행 | 이미지에 bash가 없으면 `sh`로. `k8s-master-node`, `k8s-spark-jupyter` 안에 들어가서 `kubectl`/`spark-submit` 실행할 때 씀 |
| 🔵 `docker ps` | 실행 중인 컨테이너 목록(이름, 상태, AGE 등) | AGE가 최근이면 컨테이너가 최근에 재생성됐다는 신호(Docker Desktop 재시작 확인용) |
| ⚪ `docker ps -a` | 종료된 컨테이너까지 전부 표시 | |
| 🔵 `docker inspect <컨테이너명> --format '{{json .NetworkSettings.Networks}}'` | 컨테이너의 네트워크 정보(할당된 IP 등)를 JSON으로 확인 | MinIO 컨테이너의 실제 IP를 알아내서 k3s 팟 네트워크에서 DNS 대신 IP로 접근할 때 씀. **컨테이너 재생성 시 IP가 바뀔 수 있어 매번 재확인 필요** |
| 🔵 `docker cp <컨테이너>:<컨테이너 내 경로> <호스트 경로>` | 컨테이너 안 파일을 호스트로 복사(반대 방향도 가능) | k3s의 kubeconfig(`/etc/rancher/k3s/k3s.yaml`)를 호스트로 꺼내 `kubectl`을 호스트에서 직접 쓸 때 사용 |
| 🔵 `docker restart <컨테이너명>` | 컨테이너를 재시작(재생성 아님, 내부 상태 유지) | `docker compose down/up`(재생성, 상태 초기화)과 다름 — 이 차이 때문에 복구 절차가 갈림 |
| ⚪ `docker logs <컨테이너명>` | 컨테이너의 표준출력 로그 확인 | 팟이 아니라 **컨테이너 자체**가 이상할 때(예: Jupyter가 안 뜰 때) 확인 |
| ⚪ `docker info` | Docker Desktop에 할당된 리소스(CPU/메모리) 등 시스템 정보 | Docker Desktop 크래시 원인(VM 리소스 한계) 진단할 때 확인 |
| 🔵 `docker run --rm --network <net> --entrypoint sh -v <local>:<container경로> minio/mc -c "..."` | 일회성 컨테이너를 띄워 명령 실행 후 자동 삭제 | MinIO에 마커 파일 하나만 올리는 등, 컨테이너를 계속 띄워둘 필요 없는 1회성 작업에 사용 |

## 2. kubectl — 팟/워크로드 제출·조회

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `kubectl run <이름> --image=<이미지> --restart=Never --overrides='{...}'` | 팟을 하나 즉석으로 생성해서 실행 | `spark-submit`을 담은 submitter 팟을 이 방식으로 띄움. `--overrides`의 JSON으로 `serviceAccountName`, `command`, `args` 등을 세밀하게 지정 |
| 🔵 `kubectl delete pod <이름> --force` | 팟을 강제 삭제 | 재제출 전에 이전 job의 찌꺼기 팟(Error/Completed 상태)을 정리할 때 매번 씀 |
| 🔵 `kubectl get pods -A` | 모든 네임스페이스의 팟 상태 조회(`-A` = all-namespaces) | driver/executor 팟이 `Running`→`Completed`로 가는지 확인하는 기본 명령. k3s 재생성 여부 확인에도 씀(kube-system 기본 팟만 있으면 초기화된 것) |
| 🔵 `kubectl logs <팟 이름>` | 팟의 표준출력 로그 확인 | 에러 원인 파악의 시작점(driver 이미지 미지정, RBAC Forbidden, S3 자격증명 에러 등 전부 이걸로 확인함) |
| ⚪ `kubectl describe pod <팟 이름>` | 팟의 상태·이벤트(스케줄링 실패, 이미지 pull 실패 등)를 상세히 확인 | `logs`는 컨테이너가 **떠서 실행되기 시작한 뒤**의 로그만 나오고, 스케줄링 자체가 안 되거나 이미지 pull이 실패하는 문제는 `describe`의 Events 섹션에서만 보임 |
| ⚪ `kubectl exec -it <팟> -- sh` | 실행 중인 팟 내부로 진입 | 컨테이너와 동일 개념이지만 대상이 팟이라는 점만 다름 |
| ⚪ `kubectl get pods -w` | 팟 상태를 실시간으로 계속 지켜봄(watch) | 매번 `get pods`를 반복 실행하는 대신 상태 변화가 생길 때마다 자동으로 출력 |
| ⚪ `kubectl delete pod <이름>` (force 없이) | 정상 종료 절차(Graceful)로 팟 삭제 | `--force`는 즉시 삭제(상태가 꼬여서 안 지워질 때 씀), 웬만하면 force 없이 먼저 시도하는 게 원칙 |

## 3. kubectl — RBAC / 권한

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `kubectl create serviceaccount <이름> --namespace=<ns>` | Spark driver가 executor 팟을 생성할 때 쓸 전용 계정 생성 | 기본(`default`) 서비스어카운트는 팟 생성 권한이 없어서 반드시 필요 |
| 🔵 `kubectl create rolebinding <이름> --clusterrole=edit --serviceaccount=<ns>:<sa이름> --namespace=<ns>` | 위 서비스어카운트에 `edit`(생성/수정 가능) 클러스터롤을 네임스페이스 범위로 부여 | `clusterrole=edit`은 비교적 넓은 권한 — 실무에선 팟 생성/조회만 허용하는 좁은 Role을 직접 정의하는 게 더 안전(여기선 학습 목적상 edit으로 단순화) |
| 🔵 `kubectl apply -f <파일>.yaml` | YAML로 정의한 리소스(Deployment, Service 등)를 클러스터에 생성/갱신 | History Server, `spark-live-driver-ui` Service를 이 방식으로 배포. 같은 이름으로 다시 apply하면 갱신(idempotent) |
| ⚪ `kubectl auth can-i create pod --as=system:serviceaccount:<ns>:<sa>` | 특정 서비스어카운트가 팟을 생성할 권한이 있는지 사전에 확인 | RBAC Forbidden 에러가 나기 전에 미리 검증할 수 있는 명령(에러 로그 안에서도 이 명령을 해보라고 안내가 나왔음) |

## 4. kubectl — 접속/모니터링

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `export KUBECONFIG=<경로>` | 이후 `kubectl` 명령이 어떤 클러스터 설정 파일을 쓸지 지정 | 호스트에서 k3s 컨테이너 안 kubeconfig를 복사해온 뒤 이 환경변수로 연결 |
| 🔵 `kubectl port-forward svc/<서비스명> <로컬포트>:<원격포트>` | 로컬 포트를 클러스터 안 서비스로 직결 | driver-svc(4040), History Server(18080), 라벨 기반 고정 Service 전부 이 방식으로 브라우저에서 접속 가능하게 함. **연결된 팟이 죽으면 자동 끊김**(재연결 안 됨) → 재시도 루프 스크립트로 보완 |
| ⚪ `kubectl proxy` | kubectl API 서버 프록시를 열어 `/api/.../proxy/` 경로로 서비스에 접근 | `port-forward`와 달리 팟이 바뀌어도 자동으로 새 팟을 찾아줌. 단, 이번에 Spark UI(`reverseProxyUrl`)와는 URL에 "proxy" 단어가 들어가는 구조적 문제로 **비호환 확인됨** — 대신 라벨 셀렉터 기반 고정 Service + port-forward 재시도 루프로 우회 |
| ⚪ `kubectl top pod` / `kubectl top node` | 팟/노드의 실시간 CPU·메모리 사용량 | 리소스 부족(Docker Desktop 크래시류) 원인 진단할 때 유용, 이번엔 `docker info`로 대체 확인함 |
| ⚪ `kubectl rollout restart deployment/<이름>` | Deployment를 무중단으로 재시작 | History Server 설정을 바꾼 뒤 반영하고 싶을 때 |
| ⚪ `kubectl scale deployment/<이름> --replicas=0` | Deployment의 팟 개수를 0으로(정지) | 안 쓰는 동안 리소스를 아끼고 싶을 때(완전 삭제 대신) |

## 5. MinIO 클라이언트 (`mc`)

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `mc alias set local http://localhost:9000 minioadmin minioadmin` | MinIO 서버를 `local`이라는 별칭으로 등록(엔드포인트+계정) | 이후 `mc` 명령에서 `local/버킷명/...` 형태로 참조 가능 |
| 🔵 `mc cp <로컬경로> local/<버킷>/<경로>` | 로컬 파일을 MinIO 버킷으로 업로드 | 수정한 `01.py`/`02.py` 등을 `code-bucket`에 재업로드할 때 매번 사용. **재업로드 안 하면 클러스터가 옛날 코드로 실행되는 실수가 나기 쉬움** |
| ⚪ `mc ls local/<버킷>/<경로>` | 버킷 안 객체 목록 조회 | 결과 parquet 파일들이 실제로 생성됐는지 CLI로 바로 확인할 때 |
| ⚪ `mc rm --recursive --force local/<버킷>/<경로>` | 버킷 안 객체를 재귀적으로 삭제 | 잘못 저장된 output을 지우고 재실행할 때(단, `--force`라 되돌릴 수 없으니 경로 재확인 필수) |

## 6. 네트워크/프로세스 확인

| 명령어 | 설명 | 비고 |
|---|---|---|
| 🔵 `wget <URL>` | HTTP 요청 테스트(응답 코드 확인용) | 테스트 팟 안에서 MinIO IP로 `http://<ip>:9000/minio/health/live`가 200을 주는지 확인해 네트워크 도달성을 검증할 때 사용 |
| 🔵 `curl -sL -o <파일> <URL>` | 조용히(silent) + 리다이렉트 따라가며(location) 파일 다운로드 | History Server 컨테이너 기동 시 hadoop-aws/aws-sdk jar를 즉석에서 받아올 때 사용 |
| 🔵 `nohup <명령> > <로그파일> 2>&1 &` | 터미널을 닫아도 안 죽는 백그라운드 프로세스로 실행, 출력은 로그 파일로 | `watch-4040.sh` port-forward 루프를 이 방식으로 상시 실행. **중복 실행하면 포트 충돌**이 나므로 재실행 전 기존 프로세스 확인 필수 |
| 🔵 `chmod +x <스크립트>` | 스크립트에 실행 권한 부여 | `.sh` 파일을 `./script.sh`로 직접 실행하려면 필요 |
| 🔵 `ps aux \| grep <키워드>` | 실행 중인 프로세스를 이름으로 검색 | `watch-4040.sh`가 이미 떠 있는지, orphan 프로세스가 남아있는지 확인 |
| 🔵 `netstat -ano \| grep <포트>` | 특정 포트를 누가 점유하고 있는지 확인(Linux/WSL 계열) | 포트 충돌(`Only one usage of each socket address...`) 디버깅용 |
| 🔵 `Get-NetTCPConnection -LocalPort <포트> \| Select-Object OwningProcess` | (PowerShell) 특정 포트를 물고 있는 프로세스 PID 확인 | Windows 호스트에서 `netstat`의 대체. `netstat -ano | grep`은 Git Bash 등 POSIX 셸 환경에서 씀 |
| 🔵 `Get-CimInstance Win32_Process \| Where-Object { $_.CommandLine -match "..." }` | (PowerShell) 커맨드라인 내용으로 프로세스 검색 | orphan `watch-4040.sh` 프로세스 트리 찾을 때 사용 |
| ⚪ `Stop-Process -Id <PID> -Force` | (PowerShell) 프로세스 강제 종료 | 중복/orphan 프로세스 정리 |

## 7. Airflow 도입 전에 알아두면 좋은 것 (아직 안 씀)

| 명령어/개념 | 설명 | 비고 |
|---|---|---|
| ⚪ `kubectl get deployment,svc -n <ns>` | Airflow가 만드는 워커/스케줄러 Deployment, Service 확인 | Airflow도 결국 k8s 위에서 팟을 스케줄링하는 방식(`KubernetesPodOperator`)이라 지금 익힌 `kubectl get/logs/describe` 루틴이 그대로 재사용됨 |
| ⚪ `airflow dags list` / `airflow tasks list <dag_id>` | (Airflow CLI) 등록된 DAG/태스크 목록 확인 | 지금까지 손으로 하던 "02.py 성공 확인 → 03.py 제출" 순서가 `silver_task >> gold_task` DAG로 바뀌면 이 명령으로 상태 확인 |
| ⚪ `kubectl logs -l <라벨 셀렉터>` | 라벨로 여러 팟의 로그를 한 번에 조회 | Airflow가 실행마다 새 팟 이름을 랜덤하게 만들 때, 우리가 `spark-role=driver` 라벨로 팟을 찾았던 것과 같은 방식으로 Airflow가 만든 팟도 라벨로 추적 가능 |
