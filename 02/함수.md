# PySpark 함수 정리

실습(00~02)에서 실제로 쓴 함수 + Airflow 붙이기 전에 알아둬야 할 관련 함수를 한 표로 정리. **비고**에는 셔플 여부, 비슷한 함수와의 차이를 적는다.

- 🔵 = 이 저장소에서 실제로 사용함
- ⚪ = 아직 안 썼지만 알아둬야 함(자주 쓰이거나, 알아야 헷갈리지 않는 것)

---

## 1. SparkSession / SparkContext 생성

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `SparkSession.builder...getOrCreate()` | Spark 앱의 진입점(세션)을 빌더 패턴으로 생성. 이미 세션이 있으면 그걸 재사용, 없으면 새로 만듦 | `.config()`는 반드시 `getOrCreate()` **전**에 걸어야 반영됨. 커널/프로세스가 이미 세션을 만든 상태면 이후 `.config()`는 전부 무시됨(재시작 필요) |
| 🔵 `.master("local[*]")` / `.master("spark://host:7077")` / `.master("k8s://https://...")` | 어디서 실행할지 지정(로컬 전체 코어 / Standalone 클러스터 / 쿠버네티스) | 실무 배포용 스크립트(`01.py` 등)는 코드에 `master`를 안 박아두고 `spark-submit --master`로 외부 주입하는 게 정석(재사용성) |
| 🔵 `.appName("...")` | Spark UI/History Server에 표시될 앱 이름 | 로그·모니터링에서 job 구분용, 기능적으로는 영향 없음 |
| 🔵 `.config(key, value)` | Spark 설정값(`spark.jars.packages`, `spark.hadoop.fs.s3a.*`, `spark.executor.memory` 등) 지정 | `spark-submit --conf`와 동일한 역할을 코드 안에서 함. 세션 생성 전용 — 세션 생성 후 바꾸려면 `hadoop_conf.set()` 같은 별도 API 필요하지만 **classpath에 새 jar를 추가하는 종류(`spark.jars.packages`)는 세션 생성 후엔 절대 반영 안 됨** |
| 🔵 `spark._jsc.hadoopConfiguration()` + `.set(k, v)` | 세션 생성 후 Hadoop(S3A 등) 설정값만 런타임에 바꿀 때 | jar 추가는 못하고 값(endpoint, access key 등)만 바꿀 수 있음. 우리 코드에서 S3A endpoint/키를 여기서 세팅 |
| 🔵 `spark.stop()` | 세션 종료, 클러스터에 자원 반납 | cluster 모드에서 안 불러도 job 끝나면 정리되지만, 명시적으로 부르는 게 정석 |
| 🔵 `spark.sparkContext` | 세션에서 하위 호환용 `SparkContext` 꺼내기(RDD 저수준 API용) | 신규 코드는 대부분 DataFrame API만 쓰므로 필요할 때만 |
| 🔵 `SparkContext("local", "word-count")` | RDD만 쓸 때의 저수준 진입점 (SparkSession 없이 직접 생성) | `SparkSession`이 나온 뒤로는 거의 이 방식 대신 `spark.sparkContext`를 씀 |
| 🔵 `sc.sparkUser()` | 현재 Spark를 실행 중인 OS 유저 이름 | 디버깅용, 컨테이너 안에서 `jovyan`으로 뜨는지 확인할 때 씀 |
| ⚪ `sc.setLogLevel("WARN")` | 콘솔 로그 레벨 조정(INFO가 너무 시끄러울 때) | 기능에 영향 없음, 순수 로깅 설정 |

## 2. RDD 생성

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `sc.parallelize(list)` | 파이썬 리스트를 여러 파티션으로 쪼개 RDD로 분산 배치 | 이 시점엔 실제 분산이 "계획"만 됨(lazy). 작은 테스트 데이터 만들 때 표준 |
| 🔵 `sc.textFile(path)` | 텍스트 파일을 한 줄 = 한 element인 RDD로 읽음 | DataFrame의 `spark.read.csv`보다 훨씬 저수준(스키마 개념 없음, 그냥 문자열 라인) |
| ⚪ `sc.range(start, end)` | 정수 range를 RDD로 생성 | 파이썬 `range()`의 분산 버전, 테스트용 |

## 3. RDD Transformation (지연 연산, 결과가 새 RDD)

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `map(f)` | 각 element에 함수 f를 적용한 새 RDD 반환(1:1 매핑) | **셔플 없음** — 자기 파티션 안에서만 처리 |
| 🔵 `flatMap(f)` | f를 적용한 뒤 결과를 한 겹 평탄화(flatten)해서 반환(1:N 매핑) | **셔플 없음**. `map`은 `"a b"` → `["a b"]`(1개)지만 `flatMap`은 `"a b"` → `["a","b"]`(여러 개)로 풀어줌 — 워드카운트에서 문장을 단어로 쪼갤 때 이 차이 때문에 씀 |
| 🔵 `filter(f)` | 조건 f를 만족하는 element만 남김 | **셔플 없음**, RDD/DataFrame 둘 다 있는 이름이라 헷갈리기 쉬움(RDD는 함수 인자, DataFrame은 컬럼 조건식) |
| 🔵 `reduceByKey(f)` | (key, value) 쌍에서 같은 key끼리 f로 병합 | **셔플 발생** — 같은 key를 같은 파티션으로 모아야 하므로 네트워크 이동. `groupByKey`보다 효율적(로컬에서 먼저 부분 합산 후 셔플 = combiner 최적화) |
| ⚪ `groupByKey()` | 같은 key의 값들을 그냥 리스트로 모음 | **셔플 발생**, `reduceByKey`와 달리 부분 합산 없이 원본 값을 통째로 네트워크로 보내서 훨씬 무거움 — 실무에서 웬만하면 피하고 `reduceByKey`/`aggregateByKey` 사용 |
| ⚪ `union(other)` | 두 RDD를 합쳐서(합집합, 중복 허용) 새 RDD 반환 | **셔플 없음**(그냥 파티션 리스트를 이어붙임) |
| ⚪ `distinct()` | 중복 element 제거 | **셔플 발생**(중복 판정을 위해 같은 값을 같은 파티션에 모아야 함) |

## 4. RDD Action (실제 연산을 트리거, 결과가 드라이버로 반환)

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `collect()` | RDD의 모든 element를 드라이버 메모리로 가져옴 | **위험**: 데이터가 크면 드라이버 OOM. 실무에선 큰 데이터에 절대 쓰면 안 되고, 결과가 작다고 확신될 때만(집계 후 등) |
| 🔵 `count()` | element 개수를 세서 반환 | DataFrame `.count()`와 동일 개념이지만 RDD는 셔플 없이 각 파티션 개수 합산, DataFrame은 플랜에 따라 다름 |
| 🔵 `take(n)` | 상위 n개만 가져옴 | `collect()`보다 안전 — 전체를 다 안 가져오고 필요한 만큼만 |
| ⚪ `reduce(f)` | 전체 element를 f로 병합해서 단일 값 하나로 축약 | `reduceByKey`는 key별로 여러 결과, `reduce`는 전체를 하나의 값으로 — 이름은 비슷하지만 반환 형태가 다름 |

## 5. DataFrame 읽기

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `spark.read.csv(path, header=True, inferSchema=True, ...)` / `spark.read.format("csv").option(...).load(path)` | CSV 파일을 스키마 있는 DataFrame으로 읽음 | `inferSchema=True`는 타입 추론을 위해 파일을 한 번 미리 훑어야 해서 느림 — 큰 파일은 스키마를 직접 명시하거나 Parquet으로 미리 변환(Bronze 레이어) 하는 게 정석 |
| 🔵 `spark.read.parquet(path)` | Parquet(컬럼형 저장 포맷) 파일을 읽음 | 스키마가 파일 자체에 내장돼 있어서 `inferSchema` 필요 없고, 컬럼 단위 압축이라 CSV보다 훨씬 빠르고 작음(우리 데이터 8.4GiB → 2.3GiB) |
| ⚪ `spark.read.json(path)` | JSON 파일 읽기 | 한 줄에 JSON 객체 하나(JSON Lines) 형식을 기본으로 기대함(`multiLine` 옵션 필요할 수도) |
| 🔵 옵션: `.option("header", True)` | 첫 줄을 컬럼명으로 인식 | CSV 전용 |
| 🔵 옵션: `.option("inferSchema", True/False)` | 타입 자동 추론 여부 | `False`로 끄면 전부 string으로 읽음(빠름) — 클러스터 리소스 부족할 때 이 옵션부터 끄는 게 도움 됨 |
| 🔵 옵션: `.option("encoding", "UTF-8")` | 파일 인코딩 지정 | 한글 CSV가 깨지면 `CP949`/`EUC-KR`로 바꿔서 시도 |
| 🔵 옵션: `.option("multiLine", True)` / `.option("escape", '"')` | 셀 안에 줄바꿈이나 따옴표가 포함된 CSV 파싱 | 안 켜면 필드 안 개행이 있는 행에서 파싱이 깨짐 |

## 6. DataFrame 쓰기

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `df.write.mode("overwrite").parquet(path)` | DataFrame을 Parquet으로 저장, 기존 경로 있으면 덮어쓰기 | `mode`: `overwrite`(덮어쓰기) / `append`(추가) / `ignore`(있으면 무시) / `error`(기본값, 있으면 에러) |
| 🔵 `.partitionBy(col)` | 저장 시 컬럼 값별로 폴더를 나눠 저장(Hive 스타일) | 폴더 개수 = 그 컬럼의 고유값 개수. **폴더 안 파일 개수 = 쓰는 시점의 실행 파티션 개수**라서, 사전에 `repartition(col)` 안 해두면 폴더마다 파일이 여러 개 생기는 "small file 문제" 발생 |
| 🔵 `.repartition(col)` | 지정 컬럼 기준으로 **셔플해서** 파티션을 재배치(같은 값은 반드시 같은 파티션) | **셔플 발생**(비용 있음). `partitionBy`로 저장하기 직전에 써서 폴더당 파일 1개로 만들 때 사용 |
| 🔵 `.coalesce(n)` | 파티션 개수를 n개로 줄임(셔플 없이 이웃 파티션을 합침) | **셔플 없음**(기본), 그래서 싸지만 "같은 키끼리 모아준다"는 보장이 없음. Gold처럼 이미 작은 집계 결과를 파일 1개로 정리할 때 적합. `repartition`은 늘리기도 가능하지만 `coalesce`는 줄이기 전용에 최적화 |
| ⚪ `.bucketBy(n, col)` | 저장 시 해시 버킷팅(파일을 n개로 미리 셔플해서 저장, 이후 join 시 셔플 생략 가능) | 이번 실습에선 안 썼지만 대용량 join을 반복하는 테이블에는 `partitionBy`보다 이게 더 적합할 때가 많음(단, saveAsTable 필요) |

## 7. DataFrame Transformation

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `select(*cols)` | 원하는 컬럼만 골라서 새 DataFrame 반환 | **셔플 없음** |
| 🔵 `filter(cond)` / `where(cond)` | 조건에 맞는 행만 남김 | **셔플 없음**. `filter`와 `where`는 완전히 동일(alias) — SQL 느낌 내고 싶으면 `where` |
| 🔵 `withColumn(name, expr)` | 컬럼을 추가하거나 같은 이름이면 덮어씀 | **셔플 없음**. 1번째 인자는 반드시 문자열(컬럼명) — `Column` 객체를 넣으면 `TypeError` (직접 겪은 버그) |
| 🔵 `withColumnRenamed(old, new)` | 컬럼 이름만 변경 | **셔플 없음** |
| 🔵 `drop(*cols)` | 컬럼 제거 | **셔플 없음** |
| 🔵 `dropDuplicates(subset)` | 지정 컬럼 기준 중복 행 제거(첫 번째 것만 남김, 어느 게 남을지는 보장 안 됨) | **셔플 발생**(중복 판정을 위해 같은 키를 모아야 함). `distinct()`는 전체 컬럼 기준, `dropDuplicates(['a'])`는 특정 컬럼 기준이라 더 자주 씀 |
| 🔵 `distinct()` | 모든 컬럼이 완전히 같은 행 제거 | **셔플 발생** |
| 🔵 `join(other, on, how)` | 다른 DataFrame과 조인 | **기본적으로 셔플 발생**(Sort Merge Join). `sf.broadcast(small_df)`를 감싸주면 셔플 없이 작은 테이블을 모든 executor에 복사(Broadcast Hash Join)해서 큰 쪽은 안 움직임 — 우리 self-join row 폭발 버그를 고칠 때 이 방식으로 조인 3번 함 |
| 🔵 `groupBy(*cols).agg(...)` | 그룹별 집계 | **셔플 발생**(같은 키를 모아야 집계 가능) |
| 🔵 `rollup(*cols).agg(...)` | 계층적 소계 포함 그룹별 집계(예: 업종별 + 업종×시도별을 한 번에) | **셔플 발생**. `groupBy`는 지정한 컬럼 조합 하나만, `rollup`은 앞에서부터 순서대로 계층을 줄여가며 소계까지 같이 뽑아줌(`NULL`이 소계 행 표시) |
| ⚪ `cube(*cols).agg(...)` | `rollup`과 비슷하지만 컬럼 조합의 **모든 경우의 수**로 소계를 뽑음 | `rollup`은 계층적(순서 있음), `cube`는 순서 무관 전체 조합 — 결과가 훨씬 많이 나옴 |
| ⚪ `pivot(col)` | 특정 컬럼의 고유값들을 새로운 컬럼들로 펼침(엑셀 피벗테이블과 동일 개념) | `groupBy(...).pivot(col).agg(...)` 형태로 씀. **셔플 발생** |
| 🔵 `orderBy(*cols, ascending=...)` / `sort(...)` | 정렬 | **셔플 발생**(전역 정렬은 파티션 경계를 넘나드는 재배치 필요). `orderBy`와 `sort`는 동일 |
| 🔵 `cache()` | 이후 재사용할 것을 메모리(기본 `MEMORY_AND_DISK`)에 저장해두라는 지시 | Transformation이라 바로 실행되진 않고, 다음 Action이 실행될 때 계산과 동시에 캐싱됨. 이후 같은 데이터를 여러 Action에서 재사용할 때 매번 처음부터 재계산하는 걸 막아줌 |
| ⚪ `persist(StorageLevel)` | `cache()`의 확장판 — 저장 위치/복제 수준을 세밀하게 지정(`MEMORY_ONLY`, `DISK_ONLY`, `MEMORY_AND_DISK_2` 등) | `cache()`는 사실 `persist(MEMORY_AND_DISK)`를 부르는 것뿐 |
| ⚪ `unpersist()` | 캐시/영속화 해제 | 메모리 부족할 때 명시적으로 풀어줘야 할 때가 있음 |
| ⚪ `unionByName(other)` | 두 DataFrame을 컬럼 **이름 기준**으로 합침 | `union()`은 컬럼 **순서** 기준이라 스키마 순서가 다르면 값이 엉뚱하게 섞임 — 실무에선 `unionByName`을 훨씬 많이 씀 |
| ⚪ `explode(col)` | 배열/맵 타입 컬럼을 행으로 풀어서 펼침(1행 → N행) | RDD의 `flatMap`과 개념적으로 대응되는 DataFrame 버전. `pyspark.sql.functions.explode` |
| ⚪ UDF (`@udf`, `spark.udf.register`) | 파이썬 함수를 Spark 컬럼 함수로 등록해서 씀 | 편하지만 **성능 위험**: 내장 함수(Catalyst가 최적화 가능)와 달리 Python↔JVM 직렬화 오버헤드가 커서 가능하면 내장 함수로 대체하는 게 정석. `pandas_udf`는 벡터화돼서 그나마 빠름 |

## 8. DataFrame Action / 구조 확인

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `show(n, truncate=...)` | 상위 n개 행을 콘솔에 출력 | Action. `truncate=False`면 긴 문자열도 안 자르고 다 보여줌 |
| 🔵 `count()` | 전체 행 개수 | Action, 전체 스캔 필요 |
| 🔵 `collect()` | 전체 행을 드라이버로 가져와 파이썬 리스트(Row 객체 리스트)로 반환 | RDD와 마찬가지로 **큰 데이터에 쓰면 위험**. `funnel_df.collect()`처럼 이미 작게 집계된 결과에만 사용 |
| 🔵 `printSchema()` | 컬럼명/타입/nullable 여부를 트리 형태로 출력 | 연산 아님(메타데이터만 확인, Action 아님) |
| 🔵 `describe(col?)` | count/mean/stddev/min/max 같은 기술통계 요약 | Action. 컬럼 지정 안 하면 전체 숫자 컬럼에 대해 계산 |
| 🔵 `createOrReplaceTempView(name)` + `spark.sql(query)` | DataFrame을 임시 SQL 뷰로 등록하고 순수 SQL로 조회 | 뷰 등록 자체는 연산 아님, `spark.sql(...)`이 반환하는 DataFrame에 Action을 걸어야 실행됨. DataFrame API와 결과·성능 완전히 동일(둘 다 Catalyst를 거쳐 같은 실행계획으로 변환) |
| 🔵 `explain(True)` | 이 DataFrame의 논리/물리 실행 계획을 출력 | 셔플 여부를 눈으로 확인하는 방법 — `Exchange hashpartitioning(...)`이 보이면 그 지점에서 셔플 발생 확정 |
| ⚪ `df.columns` / `df.dtypes` | 컬럼명 리스트 / (컬럼명,타입) 튜플 리스트 | Action 아님(메타데이터), 코드에서 컬럼 목록을 순회할 때 자주 씀(우리 결측치 체크 코드가 `df.columns`로 순회) |

## 9. `pyspark.sql.functions`(보통 `sf`/`F`로 임포트) 컬럼 함수

| 함수 | 설명 | 비고 |
|---|---|---|
| 🔵 `col(name)` | 컬럼 이름을 `Column` 객체로 참조 | 문자열 `"colname"`으로도 대체 가능한 API가 많지만, 연산(`col("a") * 2` 등)을 걸려면 `col()`로 감싸야 함 |
| 🔵 `when(cond, val).otherwise(val2)` | SQL의 `CASE WHEN`에 해당 | `otherwise`를 안 붙이면 조건 불만족 시 `null` |
| 🔵 `coalesce(*cols)` | 여러 컬럼 중 처음으로 null이 아닌 값을 선택 | SQL의 `COALESCE`와 동일. self-join으로 만든 여러 후보 컬럼 중 하나를 고를 때 사용(원본값 → cid 기준 → pid 기준 순서로 채움) |
| 🔵 `sum`, `count`, `avg` | 집계 함수(합계/개수/평균) | 반드시 `groupBy(...).agg(sf.sum(...))` 형태로 씀(Action 아니고 집계 plan을 만드는 것) |
| 🔵 `round(col, n)` | 반올림 | |
| 🔵 `desc(col)` / `asc(col)` | `orderBy` 안에서 내림차순/오름차순 지정 | `orderBy(col, ascending=False)`와 동일한 효과를 다르게 표현하는 것 |
| 🔵 `to_date(col)` | 문자열/타임스탬프를 date 타입으로 변환 | timestamp에서 시간 정보를 버리고 날짜만 남김(일별 집계용) |
| 🔵 `expr("percentile_approx(price, 0.5)")` | SQL 표현식을 문자열로 그대로 실행 | 근사 백분위수처럼 함수형 API에 없는 SQL 함수를 쓸 때 탈출구 |
| 🔵 `broadcast(df)` | 이 DataFrame을 join 시 브로드캐스트하라고 옵티마이저에 힌트 | **셔플이 아님** — 작은 테이블 전체를 모든 executor에 복사, 큰 쪽 데이터는 이동 안 함. join에서 셔플을 피하는 핵심 수단(단, 브로드캐스트 대상이 너무 크면 오히려 OOM 위험) |
| ⚪ `split(col, pattern)` | 문자열을 구분자로 쪼개 배열 컬럼 생성 | RDD의 `line.split(" ")`에 대응하는 컬럼 함수 버전 |
| ⚪ `monotonically_increasing_id()` | 파티션마다 증가하는 고유 ID 생성 | **순번이 연속이지 않음**(파티션 단위로 널널하게 배정) — 진짜 auto-increment PK가 필요하면 부적합, 단순 고유 식별자용 |
| ⚪ `lit(value)` | 상수 값을 컬럼으로 만듦 | 다른 컬럼과 연산하려면 상수도 `Column`이어야 하는 경우가 많아서 자주 씀 |
| ⚪ `row_number()`, `rank()`, `dense_rank()` (Window 함수) | 그룹 내 순위 계산 | `Window.partitionBy(...).orderBy(...)`와 함께 사용. **셔플 발생**(partitionBy 기준으로 데이터 재배치) — "카테고리별 매출 Top 3" 같은 요구사항에 groupBy+limit보다 정석적인 방법 |

## 11. 참고 — RDD API vs DataFrame API 이름이 겹치거나 헷갈리는 것

| 이름 | RDD에서 | DataFrame에서 |
|---|---|---|
| `map` | 있음(임의 함수 1:1 변환) | 없음(대신 `select`/`withColumn` + 컬럼 함수 조합으로 표현) |
| `filter` | 파이썬 함수를 인자로 받음(`filter(lambda x: ...)`) | 컬럼 조건식을 인자로 받음(`filter(col("a") > 1)`), `where`와 동일 |
| `distinct` | 있음, 개념 동일 | 있음, 개념 동일 |
| `count` | element 개수 | 행 개수, 둘 다 Action |
| `reduce` | 전체를 하나의 값으로 축약 | 직접 대응 없음(`agg`로 대체) |
