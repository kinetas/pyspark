# 데이터 설계 아키텍처 정리

`이론.md`에서 분리한 문서. 지금 프로젝트가 쓰고 있는 **메달리온 아키텍처**뿐 아니라, 실무에서 자주 비교되는 다른 데이터 설계 아키텍처들을 같이 정리한다. 어떤 상황에 어떤 아키텍처를 고르는지가 핵심이라, 각 장 끝에 "언제 쓰나"를 붙였다.

**중요도 기준**
- ★★★ = 실무/면접에서 계속 나오는 핵심 개념. 반드시 설명 가능해야 함
- ★★ = 알아두면 설계 토론에서 바로 도움 되는 것
- ★ = 심화/참고. 필요할 때 찾아보면 되는 것

---

## 1장. 큰 그림 — Data Warehouse vs Data Lake vs Lakehouse ★★★

데이터를 "어디에, 어떤 형태로" 쌓아둘지에 대한 세 가지 큰 접근.

- **Data Warehouse(DW)**: 정형 데이터를 스키마를 미리 정해두고(Schema-on-Write) 적재. 정형화된 SQL 분석에 최적화. 비용이 높고, 비정형/반정형 데이터(로그, 이미지, JSON 등)를 담기 어려움. 예: Oracle, Teradata, (클라우드형) BigQuery/Redshift/Snowflake.
- **Data Lake**: 원본 형태 그대로(정형/비정형 가리지 않고) 저렴한 오브젝트 스토리지에 다 쌓아두고, 읽을 때 스키마를 해석(Schema-on-Read). 우리가 쓰는 MinIO(S3 호환)가 바로 이 역할. 유연하지만 관리 안 하면 "Data Swamp(데이터 늪)"가 되기 쉬움 — 뭐가 어디 있는지, 뭐가 신뢰할 수 있는 데이터인지 알 수 없어지는 상태.
- **Lakehouse ★★★**: Data Lake의 저장 비용/유연성 위에, Data Warehouse의 트랜잭션/스키마 관리 기능을 얹은 하이브리드. Delta Lake, Apache Iceberg, Apache Hudi 같은 **테이블 포맷**이 오브젝트 스토리지 위에서 ACID 트랜잭션, 스키마 진화, 타임트래블(과거 버전 조회) 등을 가능하게 해줌. 요즘 신규 데이터 플랫폼 설계의 사실상 기본값.
  - 우리 프로젝트는 순수 Parquet(오브젝트 스토리지에 파일만 있음)이라 엄밀히는 **Data Lake** 단계 — Lakehouse로 가려면 Delta Lake/Iceberg 같은 테이블 포맷을 얹어야 함(참고 ★로만 알아두면 됨, 지금 범위 밖).

**언제 쓰나**: 정형 리포팅/BI 위주면 DW, 다양한 원천의 대용량 원본을 값싸게 모아야 하면 Lake, 그 둘을 다 원하면(요즘 표준) Lakehouse.

## 2장. 메달리온 아키텍처 (Bronze / Silver / Gold) ★★★

우리 `02` 프로젝트가 실제로 쓰고 있는 구조. **Lakehouse/Data Lake 내부를 어떻게 레이어로 나눌지**에 대한 설계 패턴(위 1장이 "어디에 쌓을까"라면, 이 장은 "그 안에서 어떻게 단계별로 정리할까").

- **Bronze**: 원본을 최소 가공(포맷 변환 정도)만 거쳐 저장. 우리는 CSV → Parquet 변환만 수행(값 정제는 안 함) — "원본을 다시 안 읽어도 되게" 만드는 게 목적. 원본 그대로에 가까워서 재처리의 안전망 역할도 함.
- **Silver**: 정제/보강. 결측치 처리, 컬럼 정리, 타입 캐스팅, 조인을 통한 보강 등 — 우리의 `02.py`(self-join으로 category_code/brand 채우기 시도, 실제로는 효과 없었다는 결론까지 포함).
- **Gold**: 비즈니스 질문에 바로 답하는 집계/요약 레이어(이벤트 퍼널, 매출 Top N, 일별 추이 등). 보통 크기가 작아서 `.coalesce(1)`처럼 가볍게 저장.
- **레이어를 나누는 이유 ★★★**: 각 레이어를 독립 job으로 두면 (1) Gold 로직만 바꿔도 무거운 원본 재처리가 필요 없고, (2) 중간 실패 시 그 레이어부터만 재시작 가능하고, (3) 같은 Silver를 여러 Gold job이 재사용할 수 있음.

**언제 쓰나**: 배치 파이프라인에서 "원본 보존 + 단계적 정제 + 소비하기 쉬운 결과물"을 동시에 원할 때. 지금 우리 프로젝트처럼 Airflow로 오케스트레이션할 계획이면, 레이어 = 태스크 경계로 그대로 매핑되는 게 큰 장점.

## 3장. Lambda 아키텍처 ★★

배치 처리와 실시간(스트리밍) 처리를 **동시에** 만족시키기 위해 나온 고전적 설계.

- **Batch Layer**: 전체 원본 데이터를 정기적으로 재처리해서 정확하지만 지연이 있는(예: 몇 시간~하루 단위) 뷰를 만듦. 우리 Bronze/Silver/Gold 배치 파이프라인이 이 레이어에 해당.
- **Speed Layer**: 최근 데이터만 스트리밍으로 즉시 처리해서 지연은 낮지만 정확도는 다소 떨어지는 뷰를 만듦(Spark Structured Streaming, Kafka Streams 등).
- **Serving Layer**: Batch 결과와 Speed 결과를 합쳐서 최종적으로 서비스/조회에 노출.
- **단점 ★★**: 같은 처리 로직을 배치용 코드와 스트리밍용 코드로 **두 벌** 만들어야 해서 유지보수 비용이 큼 — 이게 바로 다음 장 Kappa 아키텍처가 나온 배경.

**언제 쓰나**: "즉시성이 필요한 대시보드"와 "정확도가 생명인 정산/리포트"를 한 시스템에서 같이 원할 때. 다만 최근엔 스트림 엔진이 좋아져서 Lambda 대신 Kappa로 단순화하는 추세.

---

## 4장. Kappa 아키텍처 ★★

Lambda의 "코드 두 벌 관리" 문제를 없애기 위해, **모든 걸 스트리밍 하나로 통일**하자는 설계.

- 원본 데이터를 전부 Kafka 같은 로그 기반 스트리밍 시스템에 순서대로 쌓아두고(재생 가능한 이벤트 로그), 배치 처리가 필요하면 "처음부터 끝까지 다시 재생(replay)"하는 것으로 대체.
- Batch Layer와 Speed Layer를 나누지 않고 **스트리밍 처리 로직 하나**만 유지하면 됨 — 코드 중복 문제 해결.
- **단점 ★**: 전체 재처리(replay)가 스트리밍 엔진에 부담이 크고, 이벤트 로그 보존 기간/스토리지 비용이 늘어남.

**언제 쓰나**: 이벤트 소싱(Event Sourcing) 기반 시스템이거나, 실시간 처리 요구가 지배적이라 배치용 별도 코드를 유지할 이유가 없을 때.

**우리 프로젝트와 비교 ★★**: 지금 우리는 순수 배치(Lambda의 Batch Layer만 있는 상태, Speed Layer 없음) — 나중에 "실시간 이벤트도 봐야 한다"는 요구가 생기면 Lambda/Kappa 중 골라야 하는 시점이 옴.

## 5장. 차원 모델링 — Star Schema vs Snowflake Schema (Kimball) ★★

메달리온이 "레이어(Bronze/Silver/Gold)" 관점이라면, 이건 **Gold 레이어 안에서 테이블을 어떻게 설계할지**에 대한 훨씬 오래되고 여전히 널리 쓰이는 방법론(Ralph Kimball).

- **Fact Table(사실 테이블)**: 측정 가능한 이벤트(주문, 조회, 결제 등)를 담음. 우리의 `event_funnel`, `daily_purchase` 같은 집계 결과가 사실상 Fact Table의 축약판.
- **Dimension Table(차원 테이블)**: Fact를 설명하는 속성(상품 정보, 사용자 정보, 날짜 정보 등). 우리 데이터의 `category_code`, `brand`가 원래는 별도 Dimension Table(상품 카탈로그)로 있어야 할 정보 — Silver 단계에서 "카탈로그에 없는 상품은 self-join으로도 못 채운다"는 결론이 났던 게 바로 이 Dimension 정보 자체가 없었기 때문.
- **Star Schema**: Fact 테이블을 중심에 두고 Dimension 테이블들이 방사형으로 직접 연결(비정규화, 조인이 단순하고 조회가 빠름).
- **Snowflake Schema**: Dimension을 더 정규화해서 Dimension이 또 다른 Dimension을 참조(저장 공간은 아끼지만 조인이 늘어나 조회가 복잡해짐).

**언제 쓰나**: BI 툴(Tableau, Power BI, Looker)에서 바로 조회할 Gold 레이어 테이블을 설계할 때. 대부분 Star Schema가 실무 기본값(조회 성능 우선).

## 6장. Data Vault 모델링 ★

대규모 엔터프라이즈에서 "여러 소스 시스템의 데이터를 감사(audit) 가능하게, 원본을 잃지 않고" 통합하기 위한 모델링 기법.

- **Hub**(비즈니스 키 목록) / **Link**(Hub 간 관계) / **Satellite**(속성값, 변경 이력 포함)로 테이블을 쪼갬.
- 장점: 변경 이력이 자연스럽게 남고, 소스 시스템이 추가돼도 기존 구조를 거의 안 건드리고 확장 가능.
- 단점: 테이블 개수가 폭발적으로 늘고, 조회하려면 조인이 매우 많아져서 그 위에 Star Schema 같은 조회 전용 레이어를 한 겹 더 얹는 경우가 많음.

**언제 쓰나**: 여러 부서/시스템의 데이터를 하나로 통합해야 하는 대기업 데이터 웨어하우스. 지금 우리 프로젝트 규모에서는 과한 설계 — "이런 것도 있다" 정도로만 알아두면 됨.

## 7장. ETL vs ELT ★★★

데이터를 옮기고 가공하는 **순서**에 대한 구분. 메달리온/Lambda 등 위의 아키텍처들이 실제로 어떻게 구현되는지는 이 순서 선택에 좌우됨.

- **ETL (Extract → Transform → Load)**: 원본에서 추출한 뒤, 별도 처리 엔진에서 변환까지 마치고 나서 최종 저장소에 적재. 전통적인 Data Warehouse 시대의 방식 — 저장 공간이 비쌌기 때문에 "필요한 형태로 가공한 것만" 저장.
- **ELT (Extract → Load → Transform)**: 일단 원본을 그대로 저장소(Data Lake)에 적재부터 해두고, 필요할 때 그 저장소 안에서(또는 Spark 같은 별도 엔진으로) 변환. 스토리지가 저렴해지고 Spark 같은 분산 처리 엔진이 강력해지면서 요즘 주류.
- **우리 프로젝트는 ELT ★★★**: `start.py`가 원본 CSV를 **먼저 그대로** Bronze(Parquet)에 적재(Load)하고, 그 다음 `02.py`/`03.py`가 그 위에서 변환(Transform)을 수행 — 전형적인 ELT 흐름. Bronze=Load 직후 원본, Silver/Gold=Transform 단계라고 보면 메달리온 자체가 ELT 패턴의 한 구현이라고 볼 수 있음.

**언제 쓰나**: 오늘날 대부분의 빅데이터 파이프라인은 ELT(저장 먼저, 변환은 유연하게 여러 번). 실시간 변환이 저장 전에 반드시 끝나야 하는 레거시/규제 환경 정도에서만 ETL을 고수.

## 8장. Data Mesh ★★

지금까지는 전부 "데이터를 어떻게 쌓고 가공할까"에 대한 **기술적** 아키텍처였다면, Data Mesh는 "누가 데이터를 소유하고 책임질까"에 대한 **조직적** 아키텍처.

- 중앙 데이터팀 하나가 모든 도메인의 파이프라인을 다 만들고 관리하는 방식(지금까지의 중앙집중형 Data Lake/Warehouse)은 조직이 커지면 병목이 됨.
- Data Mesh는 각 비즈니스 도메인 팀(예: 주문팀, 결제팀, 상품팀)이 **자기 도메인 데이터를 스스로 소유하고, "데이터 제품(Data Product)"으로 만들어 다른 팀에 제공**하는 분산형 구조를 제안.
- 4가지 원칙: 도메인 중심 소유권, 데이터를 제품으로 취급, 셀프서비스 인프라 플랫폼, 연합된(federated) 거버넌스.

**언제 쓰나**: 조직/도메인이 매우 많고 중앙 데이터팀이 병목이 된 대규모 회사. 우리 같은 단일 파이프라인 학습 프로젝트에는 해당 없음 — "요즘 이런 이야기도 나온다" 정도로 알아두면 면접/설계 토론에서 도움 됨.

## 9장. 지금 우리 프로젝트를 이 개념들로 정리하면 ★★★

| 관점 | 우리 프로젝트의 위치 |
|---|---|
| 저장 위치(1장) | MinIO(S3 호환 오브젝트 스토리지) = **Data Lake**. 테이블 포맷(Delta/Iceberg) 없이 순수 Parquet이라 Lakehouse 이전 단계 |
| 레이어 설계(2장) | **메달리온**(Bronze/Silver/Gold) 그대로 |
| 배치/실시간(3~4장) | 순수 배치만 존재(**Lambda의 Batch Layer만 있는 상태**), 스트리밍 없음 |
| Gold 테이블 구조(5장) | 아직 정식 Star Schema는 아니고, 목적별 집계 테이블(event_funnel, category_revenue 등)이 개별적으로 존재 — 필요하면 다음 단계로 정식 Fact/Dimension 분리 가능 |
| 처리 순서(7장) | **ELT** (Bronze에 원본 그대로 Load 먼저, 이후 Transform) |
| 조직 구조(8장) | 해당 없음(1인 학습 프로젝트) |

다음 단계(Airflow)로 넘어가면, 지금의 "Bronze → Silver → Gold 손으로 순서 관리"가 `bronze_task >> silver_task >> gold_task` DAG로 옮겨가는 것 — 이건 아키텍처가 바뀌는 게 아니라, 같은 메달리온 아키텍처를 **오케스트레이션 도구로 자동화**하는 것뿐이라는 점을 구분해서 이해하면 됨.
